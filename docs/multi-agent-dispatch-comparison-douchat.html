一、执行摘要

总体判断：你的 Worker 在可靠性、边界、审计、幂等、租约/fencing、水平扩展和跨产品复用上明显更完整；douchat 在“如何决定谁来做、如何让多个 Agent 参与一轮群聊、如何把结果重新组织成对用户可读的对话”上更成熟。你的方案不是缺少一个简单的 dispatch API，而是还需要把协调语义从“可持久化的 handoff 内核”继续补成“可执行的团队工作流协议”。
你的强项
  • TeamRevision 冻结 roster/policy；TeamSession 固定一次协调生命周期。
  • Delegation + child AgentRun 原子创建，operation key 重放安全。
  • Run lease/fence、Runtime command outbox、event ACK、generation 防陈旧执行。
  • Provider-neutral；Agent Access、IM、Webhook、Autopilot 可复用。
douchat 强项
  • lead agent、single/parallel/sequential/ordered/followup/none 等群聊路由。
  • LLM 结构化规划：任务、依赖、能力、公开交付物、汇总与人工等待。
  • 参与度判断、完成度审查、故障恢复和不可用成员替换。
  • 消息/话题/群记忆/权限直接围绕用户体验闭环。

二、两套系统的真实模型

三、douchat 的分发机制拆解

1. 先判断是否需要参与

GroupDecisionService 有 lightweight participation/completion review；会区分“无需 Agent”“已经完成”“等待人类”“仍需回复”，避免每条群消息都触发全体 Agent。

2. 选择协调者和路由

模型在严格 schema 中产出 leaderMemberId、mode、memberIds、assignments、dependsOn、requiredCapabilities、publicDeliverables、waitForHuman 等。route 支持 none、single、parallel、sequential、ordered、followup、plan。

3. 规划不是执行

规划器 tool-free，有 40 秒决策 deadline；firstGroupPlan 给候选 coordinator 逐个尝试，总预算 180 秒，超时取消并丢弃迟到结果，避免重复 dispatch。

4. 结果与恢复

对失败 slot 做单独 recovery：保留已完成工作和剩余计划，可选择 skip、replace 或 pause；不会把整张计划重写。

5. 安全边界

成员权限区分真人请求与 Agent 请求；群记忆按 group/topic 隔离；规划 prompt 明确 conversation 是 data，并对结构化 JSON 和低置信度结果 fail closed。

latest message → participation / completion review → leader + route
→ plan(tasks + dependencies + capabilities + deliverables)
→ execute(single / parallel / ordered / sequential)
→ review / recover / ask human / lead summary

四、Octo 当前实现的优势与空白

已达到生产控制面水平的部分

  • 冻结配置：TeamRevision 让 active session 不受 roster 变更影响；alias 在 revision 创建时解析为稳定 agent_id。
  • 原子 handoff：CoordinationOperation、Delegation、目标 AgentSession、child AgentRun 在一个事务内持久化；payload hash 防 operation key 被改意图复用。
  • 防无限递归：handoff depth 默认 32，策略最大 128；source run 必须属于当前 TeamSession 且未终态。
  • 跨副本投递：Run lease/fence 与 runtime command enqueue 同事务；connection generation、outbox、ACK 和终态过期共同防重复/陈旧命令。
  • 解耦产品：Worker 不读 Gateway 表、不发 IM；Agent Access/IM/Buddy 各自投影 coordination event。

与 douchat 对照后暴露的空白

  1. 没有 Worker 原生的“选择谁做”协议。当前 delegate_handoff 要求调用方已决定 target alias；Worker 不提供 capability/load/health-aware candidate selection。
  2. 没有一等公民的多任务计划。Delegation 是单条 handoff，虽可递归形成图，但没有 tasks/dependencies/parallel barrier/public deliverables/summary contract。
  3. 没有统一的 partial completion/recovery 语义。Delegation 有 terminal status，但缺少“跳过某成员、替换成员、暂停等待人类、保留剩余计划”的协调状态与事件。
  4. 没有 participation/no-op 防抖。上游每次决定是否调用 Worker；Worker 本身不表达“这条消息无需 Agent 响应”或“已完成无需再派发”。
  5. 能力与权限未成为 delegation admission 的硬约束。execution_policy 可传递，但尚未像 douchat 的 capability schema 一样在 target 选择和执行前验证。
  6. 结果投影契约偏底层。Mailbox/coordination events 能记录事实，但没有标准化的 lead summary、公开交付物、引用、证据和用户可读聚合包。

五、建议增强路线（按优先级）

优先级增强项建议设计验收标准
P0Coordination Plan新增 immutable CoordinationPlan/PlanItem（task_id、target_agent、depends_on、capabilities、expected_output、public_deliverable）；PlanItem 映射 child AgentRun，依赖满足后才 admission。支持 parallel/sequential/barrier；重复提交不重复创建 child Run；单项失败不丢失已完成项。
P0能力、负载、健康感知 admissionTeamRevision 声明 capability；Runtime/Agent readiness 暴露能力与 bounded health；Worker 在 dispatch 前校验，调用方只能给 preferred target，不能绕过 policy。不满足 capability/权限/Space 的 target 在事务内拒绝；记录明确 rejection code。
P0协调恢复状态机增加 replace|skip|pause|retry_same 的 CoordinationOperation；恢复只作用于失败 slot，保留原 plan hash、completed items、attempt history。故障成员替换不会重跑已完成工作；pause 能等待人工输入并安全 resume。
P1Participation/no-op contract上游仍负责产品语义；Worker API 可接受 admission=none|single|plan 或返回 needs_agent=false 的可审计决策，但不把 LLM prompt 放进 Worker 核心。重复 IM 事件、已完成任务、明确静默请求不会生成无意义 Run。
P1统一结果包与证据增加 CoordinationResult：summary、item_results、public_deliverables、citations/artifacts、blocked_reason、human_question；Worker 保存事实，Gateway/Access 负责渲染。同一结果可被 IM 卡片、Task 页面、Webhook JSON 复用。
P1Mailbox 可恢复输入增加 causal sequence、visibility、ack/lease、dedupe key、reply_to；Agent wakeup 要求 source run/plan item fence。断线重连不丢消息；同一 mailbox message 不被两个 Run 消费。
P2观测与成本控制指标补充 plan depth、fan-out、critical-path、per-item queue wait、planner/admission latency、replacement rate、token/cost budget。可回答“慢在规划、排队、Runtime 还是 provider”，并可限制最大 fan-out/预算。

六、推荐的目标分层

产品入口（IM / Task / Webhook / Buddy）
  └─ 消息语义、是否需要回复、用户展示、delivery
       ↓ submit TeamSession / CoordinationPlan
Agent Worker（权威协调控制面）
  ├─ 冻结 TeamRevision / policy
  ├─ admission：capability、权限、健康、负载、预算
  ├─ PlanItem DAG + Delegation + AgentRun
  ├─ lease / fence / outbox / ACK / recovery
  └─ CoordinationResult / events / mailbox
       ↓ run.start
Octo Runtime Runtime → Adapter Host → Provider
关键原则：借鉴 douchat 的“决策语义”，不要复制它的“本地群聊实现”。规划器可以在 Agent Access 或独立 Coordination Planner 中运行，Worker 只接收经过 schema 校验的计划并负责权威 admission、持久化、执行和恢复。

七、最终结论

你的方案总体方向是对的，而且底座比 douchat 更适合生产化。最值得增强的不是 transport、AgentSession 或 Run 状态机，而是上层协调协议：从单步显式 delegate_handoff 演进为可验证的 Plan/PlanItem、能力感知 admission、slot-level recovery 和统一结果包。

如果只做一件事：优先实现 CoordinationPlan + PlanItem DAG + capability admission + replace/skip/pause recovery。不建议把 douchat 的 LLM planner、群记忆或消息表直接塞入 Worker；应由上游 planner 生成结构化计划，再让 Worker 做不可绕过的策略、幂等、租约和执行权威。
