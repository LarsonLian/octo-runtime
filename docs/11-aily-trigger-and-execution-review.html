Research refresh / target architecture

Aily 触发研究与 Octo 统一 AgentRun 架构

保留 Aily 多入口、任务协作与 provider resume 的研究证据；Octo 的目标定义直接统一为 AgentSession / AgentRun，业务调度不进入 Engine Worker 或 Runtime。

结论

Aily 展示了 manual、event、schedule 与 IM 等入口可以驱动长期工作，也说明业务 Task 与本地 provider invocation 不是同一个对象。Octo 不复制 Aily 的 Task Run / Session Run 多层状态机，而是在 Worker 中保留一个执行实体 AgentRun。

统一调用：业务服务提交 namespace + agent_id + session_key + trigger_occurrence_id + input。Worker 解析 AgentSession、排队和 lease；Runtime 只执行。

三层所有权

Business

Loop / AutoPilot / Webhook / IM

拥有触发器、父子任务、业务 attempt、投递策略和业务状态。每次应执行的事实由它们决定。

Control

Agent Worker

拥有 Agent、revision、AgentSession、AgentRun、状态机、lease、fencing 与 provider resume binding。

Runtime

Octo Runtime

拥有 invocation、provider 子进程、事件翻译、可靠 outbox；不拥有业务调度。

Aily 概念如何落到目标架构

Aily 研究对象保留的结论Octo 目标定义
Trigger / Auto入口规则和 occurrence 必须 durable规则与 occurrence 留在业务 namespace；命中后提交 AgentRun
Task / Task Run长期交付与某次执行不可混同Loop 持有 Task/Attempt；每次尝试引用一个 Worker AgentRun
Session Run每轮消息、工具和终态需要稳定归属统一为 AgentRun，不再建立第二套 SessionRun
Invocation本地调用要可取消、可观测Runtime 本地 invocation；不是业务 Run
Provider Session恢复标识由 provider 定义opaque 数据保存在 Worker AgentSession

身份与去重

AgentSession identity:
  (namespace, agent_id, session_key)

AgentRun occurrence identity:
  (agent_session_id, trigger_occurrence_id)

Examples:
  im        + agent_1 + v1/octo/endpoint_1/group/group_9
  loop      + agent_1 + v1/task/task_42
  autopilot + agent_1 + v1/automation/auto_7/repo_main
  webhook   + agent_1 + v1/source/hook_3/repo_main

trigger_occurrence_id 比抽象的 idempotency key 更具体：它表示真实发生的一次入口事件。相同 occurrence 与相同请求返回原 Run；同 ID 携带不同请求必须冲突。

状态不可机械复制

状态机示例权威
业务工作todo / in progress / review / blocked / doneLoop 等业务服务
AgentRunqueued / leased / running / interacting / cancelling / terminalAgent Worker
Invocationaccepted / executing / stoppedRuntime
Deliverypending / delivered / failedChannel Gateway / delivery worker

Run completed 可以把 Loop Task 投影成 in review；delivery failed 也不会反向把已完成的 AgentRun 改成 failed。

端到端时序

Business scheduler
  -> Agent Worker: submit AgentRun
  -> Worker DB: get/create AgentSession, dedupe occurrence, queue Run
  -> Runtime: run.start + lease/fencing + optional provider_session
  -> Provider: start or resume
  <- Runtime: run.event(seq), session.update, terminal
  <- Worker: durable ACK and authoritative state
  <- Business: projection / delivery

IM 与 schedule 的差异止于业务入口和最终 delivery。进入 Worker 后它们执行完全相同的 AgentRun 协议。

Reset

Worker reset 增加 session generation/provider epoch、清空 provider session，并按策略取消旧 Run。下一次调用没有 resume ID，provider 创建新 thread/session，再由 session.update 回写。Runtime 和业务服务都不自行拼接 provider thread ID。
