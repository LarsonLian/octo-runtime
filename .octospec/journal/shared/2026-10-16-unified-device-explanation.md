按最新要求在 WebUI 定位说明后增加 CLI 使用手册链接，作为已有内置 Extra 插件具体使用方式的入口；同步任务记录中的 Loop 定义、本地绕云端反例及验收口径。

按最新澄清，讲解正文直接定义 Loop daemon 为“Loop 中专家执行业务任务的专用执行程序”，说明其轮询、领取与执行 Loop 任务的职责；删除正文中 checkout、登记快照与历史能力核对的解释，避免干扰业务定义。源码核对不代替用户提供的历史架构事实。

按最新补充明确复用旧 Loop daemon 的调用代价：Buddy 或 IM 先转换成 Loop 调用模型，经 Loop 云端服务，再由本机 daemon 轮询领取执行。即使调用方与执行实例同机仍绕经云端，因此不满足核心目标 1 的本地直接 IPC；此例限定为复用旧 Loop 执行链路，不把 IM 消息通道本身的网络传输混作本地 IPC。

按最新要求将结尾的 WebUI SSE 说明改为插件定位：现有 webui-extra 提供类似 OpenClaw 的 WebUI 能力，仅用于本地服务调试，不用于实际生产环境；同步架构规则中的插件说明。

按最新澄清区分移动端 Buddy 的 IM 对话与 conversation 跨端对话：IM 入口经 wukong-im Server / IM Channel 收发消息；conversation 入口像桌面本地对话一样指定设备发起 AgentRun 并接收结果。业务价值章节改为按入口说明，表格拆为两行，目标图增加两类移动端节点及各自接入关系。旧架构的额外待建移动端链路限定为 conversation 跨端对话，具体生产方案继续标待确定；不增加产品代码或会话协议。

按最新要求删除讲解中 machineId / runtimeId 映射、归属、认证授权的整段说明。架构定义同步收窄：这些对外身份与业务模型属于可选 Extra，不是统一设备必备概念；历史虚拟身份说明保留历史用途，不作为设备本体要求。本次不改变现有实现、身份文件或配置，已启用接入的权限校验仍按其合同执行。

按最新要求统一进入 AdapterHost 的箭头标注为 ipc_invoke，覆盖本地 IPC、Channel Gateway、候选设备接入模块及寻址分流图；架构规则图也按每个来源分别标注。仅修改讲解标签，不新增或改名 SDK / RPC 方法，不改变实际进程与传输合同。

按最新要求简化旧 Workspace Runtime 段落：突出 workspace_id 绑定、按 Workspace 重复登记，以及设备身份与业务权限耦合造成个人、组织、项目归属难以统一声明。讲解正文移除执行次数与历史合同的绕行解释，TRD 留在来源链接；统一设备以稳定本地身份、独立云端归属表达目标。现有材料未核实用户加入 Workspace 后立即自动复制的触发实现，不作此断言，也不新增登记协议或声称已支持所有归属类型。

按最新要求将文档开头归纳为三个并列核心目标：本机应用通过 IPC 执行任务；IM Channel 接收 wukong-im Server 下发的消息并触发执行；可选注册设备为线上可用，支持移动端 WorkBuddy 指定设备对话。目标图同步标明 wukong-im Server 与消息下发，设备 Token 和模块候选方案留在后续接入说明，不把线上登记作为本地调用或 IM 通道的前置条件。

[讲解入口](../../../ARCHITECTURE.md)按四个问题组织，包含旧 IM 链路、目标设备结构、寻址分流三张 Mermaid 图。旧 IM 按用户给定基线描述为 IM → OpenClaw 内置 Channel → Agent 执行，没有统一设备概念；其执行位置隐含于 Bot / Channel，不能当作跨业务的统一执行地址。

按用户最新补充展开旧架构图：IM → OpenClaw 内置 Channel；桌面 OctoBuddy → 本地启动 Codex App Server / 直接 IPC；Loop → 专用 daemon 的 Loop 轮询执行流程。将移动端从已有业务入口移出，使用独立虚线框、节点和连线标为缺口，说明达到 WorkBuddy 跨端效果需要额外实现一套远程接入、设备寻址与执行链路。桌面本地 IPC 已存在，统一设备补充的是跨业务设备发现、寻址与调用。历史 Loop 执行链与旧仓当前登记阶段快照分别描述。

按用户截图纠正旧架构图布局：移除下层执行实现的嵌套小框，保留业务入口、执行实现两层大框及三对一一对应的节点，避免下层自动重排引起连线交叉。移动端的说明同步改为需要额外实现一套，不使用无法实现的表述。

旧 Loop daemon 是另一个业务专用客户端。核对其 README、start.go 和 gateway 协议后，说明登记、报告与启动凭据耦合；没有将其画成旧 IM 执行路径，也没有声称其已完成 Attempt Claim 或执行。

按用户进一步澄清，将缺少跨业务普适性列为旧 Loop daemon 不满足统一设备定义的首要原因：大量 Loop 应用业务逻辑耦合在服务内，其他业务几乎无法直接复用。新架构由 Extra / 业务服务承载应用逻辑，新业务经 Extra 或 SDK 接入，设备内核无需理解该业务对象、状态和流程；同步讲解入口及架构规则。

补充具体反例：Buddy / IM 必须转换为 Loop 调用模型，意味着应用专用模型成为公共执行的前置条件。目标是各业务独立适配公共合同，Loop 为使用方之一。核对旧仓 TRD 的背景和 7.2 节：旧版每 Workspace 注册 Runtime 曾造成重复与漂移，该 TRD 已提出取消；文档按历史问题说明多个业务记录可能映射同一设备，不据此推断一次请求广播、多次执行或该仓当前仍按 Workspace 登记。

[架构规则](../../rules/architecture.md)定义设备为机器上特定 Runtime Home 承载的本地执行实例，区分 Home 级 machineId 和虚拟 runtimeId。明确目标是调用方及业务接入先解析目标，本地直连 IPC，异地经业务云端接入，具体接入模块与分工待架构确认。既有身份与状态保护继续有效。

按后续要求将移动端远程 AgentRun 提为核心目标；现有设备模型可通过 Extra 扩展接入，设备本地存在不依赖云端登记。未注册或注册失败不影响本地 IPC，缺少有效映射会导致对应跨端寻址失败；注册、权限、在线和执行成功分别表达。三图全部采用 TB，同类调用端、云端服务、设备组件及传输通路用 subgraph 分组。

按最新澄清撤回对共享访问 Extra 的具体职责划分：图中改为「可能的 Extra（待架构确认）」，仅表达设备登记与在线状态保持。删除该模块到内核的 invoke 接线及云端向它下发任务的既定关系；远程调用仅示意目标，具体模块分工待架构确认，不预先归入授权、远程请求处理或结果回传。

后续补充明确远程服务不直接连接执行内核：两张目标图改为云端连接 Extra 层设备接入模块、接入模块本地调用 AdapterHost。设备登记与在线状态保持考虑由该独立模块承载，使用独立设备 Token；模块具体方案、Token 合同及调用接线仍待架构确认，不展开其他职责，也不把云端登记或设备 Token 变成本地 IPC 的前置条件。此补充取代前一轮云端到内核的抽象直连箭头。
