# 已接受决定

F29 用户确认：**设备执行内核 + Extra 插件 + 外部工具**的形式，已经清楚划分接入、身份和执行权限，满足本项目标架构。保留当前分工，不新增 Channel 混合权限中心，不迁入旧 Gateway 的 minimal/host 分档和专用业务 broker。

这不是“减少权限检查”，而是让每类判断留在有真实依据、能够执行该判断的组件。F29 的三类职责目标覆盖 100%；这不表示旧实现的每一种隔离机制均已等价实现，也不表示其他已记录缺陷已修复。本轮仅记录决定，不修改代码或配置。

## 谁决定什么

| 主体 | 决定或执行的事项 | 不由该主体代替的判断 |
| --- | --- | --- |
| Extra，IM 场景为 ChannelGateway | 校验真实发送者、Space、群范围及 @ 等接入条件；组织本轮业务输入与 Context；按自身合法 Bot 配置提供工具执行身份；管理本渠道的会话、连接和回复 | 准入不授予发送者个人资源权限；不定义第二套本地执行权限，也不代执行业务工具 |
| 设备执行内核与 Adapter | 按统一执行合同校验和传递输入、管理执行生命周期；通过统一 approval_policy 表达执行权限，由 Adapter 映射 Provider 原生行为并返回真实结果 | 不因某个 IM 业务增加通用产品策略、业务资源 ACL 或 Gateway 工具权限矩阵 |
| Agent 与外部工具、服务端 | Agent 按业务 Context 在工具循环中完成业务动作；CLI/MCP 等实际工具使用对应凭据，工具与服务端校验资源 ACL 并返回结果 | 不以“已获准触发”或 full_access 代替服务端授权，不把业务调用失败转交 Channel 代执行 |

HostApp 仍负责组件装配、配置来源与安装决策；SDK 宿主按公开接口组合组件。外部工具指执行具体业务操作的 CLI/MCP 等能力，不要求所有工具都经云端调用，也不禁止标准 MCP。

## 当前架构的实际收益

1. **权限含义明确。** “谁能发起”“以谁的身份访问资源”“本地允许执行什么”分别判断。已授权用户请求读取文档时，Channel 判断能否触发；工具以配置的 Bot 身份访问；服务端判断 Bot 能否读取该文档。本地 full_access 不会因此扩大文档权限。
2. **执行内核可跨业务复用。** IM 和其他业务入口使用同一执行合同；内核无需理解群规则、文档业务或文件交付流程。新增业务主要在对应 Extra、Context 和工具中实现，不要求内核加入该业务的分支。
3. **业务与 Provider 可以分别演进。** 新增业务工具不需要让 Channel 再封装一遍 API；Provider 差异集中在 Adapter 的原生适配。避免每增加一种工具或引擎，都修改 Gateway 内交叉组合的权限矩阵。
4. **重复配置和状态更少。** 不为已有准入、执行审批和资源 ACL 增加另一套同义分档；不为了代理业务工具再持有一套业务租约与执行流程。Extra 按整体公开生命周期管理，宿主无需依赖内部 Bot 或连接对象。
5. **错误更容易归责。** 准入拒绝查 Extra，Bot 身份传递错误查执行环境链，资源拒绝查工具与服务端，本地执行拒绝查统一策略与 Adapter。修复最先违反合同的组件，避免下游补偿掩盖问题。

这些是职责分离带来的设计收益，不是本轮性能、安全性或线上可靠性的实测结论。

## 旧设计及评审中的教训

旧 Gateway 的 capability 分档包含真实的工具、网络和 Provider 参数策略；trustedInput/groupPolicy 处理触发范围；专用 MCP broker 还通过会话租约和工具列表，将业务调用送入 Gateway 的 IntentExecutor。问题是这些不同责任集中装配后，容易被误认为一个必须整体复制的“权限功能”。具体代码与差异依据见 [F29 评审](../../tasks/gateway-august-feature-assessment/assessment.md#逐项-reviewf29-权限分档与工具网关)。

以下同时记录已核对的旧机制和本轮明确拒绝的扩展方向；不把所有拒绝方向都写成旧仓已有实现。

| 教训 | 为什么会形成问题 | 后续必须遵守的边界 |
| --- | --- | --- |
| 将准入、工具身份和本地执行权限合成 Gateway 档位 | 一个档位牵动不同作用域的策略，容易把“可以触发”误读成“可以访问资源或操作本地文件” | 按三类判断分别确定责任和依据；不恢复同义分档或 Channel 跨 Provider 权限矩阵 |
| Gateway 专用 broker 同时承担业务代理 | Gateway 除了通信和接入，还需跟随工具清单、业务 API、租约及执行副作用变化，扩大改动范围 | Agent 使用明确提供的业务工具；真实工具与服务端负责授权。标准 MCP 仍按原生合同接入 |
| 在 Channel 中硬编码业务收尾或补做工具动作 | 模型执行和 Channel 可能分别产生副作用，失败、取消和重复执行难以按单一合同判断 | 非必要的业务步骤通过 Context v3 约束 Agent；工具或适配违约在责任模块修复，不以提示词掩盖代码错误 |
| 为少数场景让宿主控制 Extra 内部 Bot、连接或局部重载 | 宿主依赖插件内部结构；接口、状态和失败处理成本超过主要单机单 Bot 场景的收益 | 保持 Extra 整体生命周期和最小公开接口；沿已接受的整体重载方案，不另造逐 Bot 控制合同 |
| 按旧代码结构统计新架构的功能缺口 | 不同承载方式被误判为能力缺失，最终以“补齐功能”为名恢复旧耦合 | 先确定真实业务目标和责任，再评估覆盖；明确排除的机制不是待补功能，已定位缺陷仍单独记录 |

业务流程的详细约束沿[工具调用决策](2026-10-16-agent-toolcall-channel-boundary.md)，插件生命周期的需求价值和取舍沿[Extra 整体边界决策](2026-10-16-extra-whole-plugin-boundary.md)，本记录不另造一套协议。

## 防止后续重复的评审要求

新增接入、权限或业务工具需求时，方案必须说明判断对象、作用范围、真实输入和唯一责任组件。若已有合同能够表达需求，复用该合同；若确有缺口，在责任组件补齐，不以增加“统一管理层”代替责任分析。

评审必须区分业务指引与安全校验：Context 约束行为，不能授予身份、绕过审批或替代 ACL。也必须区分协议适配与业务代执行：CanonicalEvent 投影、标准交互响应和最终回复属于 Channel 的正常责任，不能以本决定删除；模型业务动作仍归工具循环。

出现“Channel 再调一次业务 API”“宿主访问 Extra 内部 manager”“新档位同时控制触发与文件权限”或“Host 自动补业务 Context”等方案时，按对应现行规则纠正归属。该要求不新增用户审批流程，也不禁止已有明确合同所需的协议校验、执行权限、取消、预算和资源清理。

## 适用范围与未解决事项

- F29 新增需求必要性 0/100、保留方案可执行性 95/100、三类职责目标和当前覆盖 100%。剩余 5 分是不同 Provider 版本的权限/审批实测证据限制，不是已定位的 5% 待补代码。
- full_access 不扩大 bf_token 资源权限或 OS 权限。独立配置的 MCP 凭据和环境优先级仍按其真实合同，不能声称任意 MCP 都自动使用本 Bot 身份。
- OpenClaw 沿已接受的实例启动环境合同，不声称逐 Run 注入。F24 的 OpenClaw 配置候选筛选缺陷仍待修改，不被本项 100% 结论覆盖。
- 不承诺等价复制旧逐工具 allow/deny、统一禁网及 broker 凭据隔离；确有新需求时按具体合同重新评估，不能仅因旧仓存在就恢复。

现行约束入口为[基础架构](../../rules/architecture.md#设备执行内核extra-与外部工具的职责权限边界)和[渠道接入](../../rules/channel-integration.md#im-agent-业务边界)。未来修改对应核心代码时，可在必要的边界注释中引用本记录或相关规则，避免重新解释为缺少旧 Gateway 功能。
