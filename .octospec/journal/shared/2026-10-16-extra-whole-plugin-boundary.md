# 已接受决定

用户在 F20 评审中确认：channel-gateway 作为一个完整 Extra 接入，加载和卸载的单位都是插件。宿主负责准备完整配置，并通过已有核心接口加载、卸载和查询状态；不得跨入插件内部直接操作某个 Bot、连接管理器、Worker 或内部队列。配置改变时，宿主卸载对应 Extra，保存并提交最新完整配置，再加载插件。

这一决定适用于 Extra 的模块边界，不限于 Octo Bot。逐 Bot 无中断热更不纳入当前目标，也不预留对应的通用控制接口。保持当前 octo-runtime 架构是已选方案，不是暂时缺少热更实现。

本轮仅更新 Octospec，不修改源码、测试、实际配置或进程。当前加载接口和既有验收依据见 [Extra 合同](../../rules/extras.md)与[责任边界任务](../../tasks/extra-responsibility-boundary/brief.md)。

## 先看谁会受益，再决定增加什么

按用户明确的当前产品部署判断，主要场景是单机单 Bot，大部分 Bot 是独立部署实体。用户进一步估计，仅约 1% 的用户或设备可能采用同机多 Bot；其中还要发生单个 Bot 配置更新，才可能从局部热更受益。这个 1% 是用户提供的业务估计，不是本轮采集的部署统计，也不是代码中的阈值或配置。

对单机单 Bot 来说，配置改变时，当前 Bot 无论如何都需要使用新配置重新建立连接。整体重载没有额外的其他 Bot 可被连带断开。因此，之前笼统强调“改一个 Bot 会影响其他 Bot”，把少数部署的情况放大成主流成本，不能作为增加局部热更的理由。

局部热更相对整体重载的实际收益，主要是同机多个 Bot 时，改动一个 Bot 可以让其他 Bot 保持原连接。用户接受该少数场景在配置变更时短暂重连；当前没有需要为其提供无中断更新的业务要求。这不是否认连接体验的价值，而是根据受益范围与发生时机选择合适的工程投入。

## 为什么局部热更不只是多加一个方法

如果宿主能直接更新某个 Bot，就必须知道插件内部有哪些账号、如何标识、哪些字段需要重连，以及新增、删除、停用和更新分别意味着什么。插件内部结构由此进入宿主与框架的公开合同。未来接入其他 Extra 时，账号可能变成订阅、监听端口或其他业务对象，通用框架又需要增加新的业务控制分支。

指纹比较和 reconcile 还会引入更多必须长期维护的行为：配置以哪一份为准、更新与卸载同时发生时谁先执行、部分更新失败如何表达、旧连接与排队任务何时退出、宿主保存成功但插件应用失败时如何恢复。即使没有事务回滚要求，也必须明确这些并发与失败合同，不能只计算一段配置比较代码的开发量。

收益集中在少数部署的一次配置更新，接口、状态和测试成本却需要每个宿主、插件维护者及后续接入方持续承担。按照当前需求，这种投入不成比例，属于过度设计。模块整洁的实际价值是：增加一种 Extra 时，只需实现稳定的加载、清理和状态合同，无需让 Runtime 学会该插件的内部业务对象。

## 函数式入口为什么能守住边界

Extra 对外提供加载函数，宿主传入完整 config 和包含执行能力、signal、onDispose、onStatus 的 context。加载函数负责建立本插件的内部结构，通过闭包持有连接和状态，并注册清理与状态回调；宿主只按既有合同调用入口、发出停止信号并等待清理，不需要取得内部 manager 或逐个管理 Bot。

这种函数式接入把“如何实现插件”留在函数封装内部。插件可以调整内部类、账号组织、连接与任务流程，只要核心函数合同保持稳定，就不要求宿主同步修改。函数内部可以维护必要的资源和状态，生命周期通过已注入的回调收敛；不额外设计一套公开插件对象或对外的逐 Bot 方法集合。

Host App 和 Host CLI 都必须遵守这个边界。不得把封装在加载函数内的流程搬到宿主，令宿主负责判断哪个 Bot 要重启、依次关闭哪些连接、如何更新队列或向内部对象下发命令；也不得以透传任意请求的方式绕过边界。宿主负责插件整体的配置与生命周期编排，插件负责内部业务流程。

因此，维持函数式入口和少量核心接口直接服务于独立扩展与长期维护。仅约 1% 的潜在同机多 Bot 场景，不足以要求每个接入方都依赖插件内部结构；为少数场景增加内部控制面，会让原本简单的函数接入演变成跨模块的业务管理协议。

## 宿主与插件如何协作

| 主体 | 可以做什么 | 不得扩大为什么 |
| --- | --- | --- |
| 宿主 App / CLI | 读取和保存自己的配置；按插件公开 schema 构造完整对象；决定整体加载、卸载时机；展示插件公开状态 | 直接调用内部 manager.upsert/remove、操作单条 WS、比较内部连接指纹，或要求通用逐 Bot 控制接口 |
| SDK / daemon / loader | 按插件名称管理生命周期，传递完整声明和停止信号，等待清理，转发状态及真实错误 | 理解 Bot 字段、计算业务差异、根据状态自行更新内部对象或为某个平台增加生命周期分支 |
| Extra | 消费加载时收到的配置；管理内部账号、连接、重连、路由和业务状态；停止时释放资源 | 接管宿主配置来源与持久化，或把内部管理工具升级为宿主必须依赖的公开协议 |

宿主可以了解公开配置和状态，桌面也可以保留逐 Bot 编辑界面。限制的是运行控制边界：界面编辑一个字段，仍由宿主生成最新完整配置并重载所属 Extra；界面粒度不要求底层增加同粒度的运行时命令。

例如，同一 channel-gateway 中配置 A、B 两个 Bot，修改 A 时仍整体重载该 Extra，B 可以重连；若只有 A，则不存在 B 的连带影响。插件内部可以使用任何合适的数据结构管理 A、B，但宿主不得据此依赖其私有方法。正常重载一个 Extra 不应重启其他 Extra 或共享 AdapterHost。

## 接受重连，不等于忽略清理和错误

SDK/桌面按“卸载对应 Extra → 保存配置 → 加载完整声明”操作。CLI 当前只通过 extraset 保存并返回 reload_required，之后以 daemon restart 生效；CLI 的重启范围大于单个 Extra，这是现有入口的实际边界，不应混写成单插件重载，也不由本决定新增 CLI 控制命令。

整体重载仍须发出停止信号并等待资源清理；清理失败必须报告，不能假装卸载完成后再建一份连接。保存成功、加载成功、外部 Bot 在线分别表达。不承诺在途任务无损迁移或配置失败自动回滚，取消和结果未知按既有合同处理。接受配置更新时的正常重连，不授权任意丢失任务、忽略失败或频繁重启。

## 后续评审如何守住边界

不能仅凭“技术上能做”“旧 Gateway 已有”或“极端情况下可以少断一次线”扩大公开接口。提出同类需求时，先说明真实部署中谁受到影响、频率和损失、完整配置重载为何不能满足，再评估接口耦合、状态、并发、失败与长期维护成本。当前这些收益不足以支持逐 Bot 热更，因此不实施、不预留、不作为欠项。

未来若业务场景实质变化，应先依据新的需求和证据重新评估责任归属；在此之前继续遵守本决定，不能以未来可能需要为由提前破坏现有模块合同。F20 的既定配置生效目标覆盖 100%，保持删除线，新增必要性 0/100、可执行性 95/100；详见 [F20 评审](../../tasks/gateway-august-feature-assessment/assessment.md#逐项-reviewf20-配置监测与局部热重载)。
