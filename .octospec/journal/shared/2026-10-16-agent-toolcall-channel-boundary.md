# 已接受决定

此决定适用于所有类似的定制业务执行流程。非基础设施合同所必需的步骤、顺序、条件、工具选择和收尾要求，统一由业务发起方通过 octo.context-envelope/v3 注入约束，交给 Agent 的工具循环执行；严禁在 Channel、Host、Adapter 或其他中间层新增专用流程代码代执行。以下文件交付仅是具体例子，不是此约束的适用上限。

用户在 F11/F12 逐项评审中确认：消息发送、文件上传、附件交付与多文件处理是 Agent 的 tool call 能力。已有 octo-cli 能完成的业务动作，计入当前目标能力覆盖；不要求 Channel 再实现一套 API 或中间业务流程。旧 Gateway 的执行后自动 artifact 投递属于历史遗留实现，不作为 Runtime 同步目标。

“生成产物后自动交付”是 Context instructions 的要求：业务方可以在本轮 Context 中提供任务约束，Agent 据此在自身工具循环中选择文件、上传、发送并检查结果。**严禁在 Channel、Host 或 Adapter 中硬编码“执行结束 → 收集 artifact → 上传 → 发送”的业务流程**，也不得解析模型正文、路径标记、工具输出或 artifact 事件来替 Agent 补做交付。

本轮只固化架构与评审状态，不修改代码、实际提示词、工具或配置，不上传/发送文件，不宣称本 Agent 完成线上复测。

## octo-cli 的维护归属与预置价值

用户明确：octo-cli 当前由业务团队共同维护，是使用 Go（Golang）开发的二进制可执行程序，主要提供 Octo 生态各业务子系统的 API 调用能力。它不是 Runtime CLI（octo-runtime）；Runtime CLI 是执行宿主，octo-cli 是 Agent 可以使用的业务工具。

预置 octo-cli 对 Octo Runtime 产品具有重要价值，ChannelGateway 的 IM Channel 是典型场景。在工具可用、身份和资源权限满足要求时，Agent 可以根据对话任务读取文档、调用业务 API、发送消息、上传并交付文件。用户不必在每一步手工切换业务系统，产品由对话入口延伸为能够完成业务操作的 Agent。用户将此评价为体验上的质的提升；这是产品价值判断，不是本轮量化测试结果。

例如，用户要求“读取指定文档，整理报告后发到指定会话”，业务方提供材料和要求；Agent 在工具循环中调用 octo-cli 读取、生成并交付，工具返回实际权限和执行结果。这个示例表达预置工具带来的完整业务体验，不表示 Channel 应新增固定读取、上传或发送流程，也不证明本轮已执行该任务。

维护边界固定为：业务团队维护工具的业务 API 调用能力；HostApp 团队决定预置、版本、安装方式和配置；Runtime 提供通用执行及身份传递。实际指引由业务方通过 Context v3 提供，Token 不进入模型文本。预置价值不等于 Runtime 强制依赖或执行层隐式安装，本轮不安装工具、不修改配置、不发送消息。

## 指令与执行归属

| 主体 | 责任 |
| --- | --- |
| 业务发起方 | 决定本轮是否要求文件交付，提供目标、材料和匹配现有工具的 Context 指令，并随 Event 保存协议快照 |
| Agent / Provider Harness | 理解任务，在工具循环中决定并执行需要的查询、生成、上传和发送，读取真实结果，处理逐项成功或失败 |
| octo-cli / 实际工具 / 服务端 | 执行被调用的操作，校验真实身份、权限和输入，返回实际结果与错误 |
| Channel | 真实 IM 准入、业务输入及 Context 组织、执行接线、CanonicalEvent 呈现、标准交互响应、当前会话回复与连接生命周期；不代替 Agent 执行业务工具 |
| Host / Adapter | 按统一合同校验、渲染、传递并进行原生适配；保留工具执行、审批、取消和预算边界，不增加业务收尾任务 |
| HostApp | 决定是否提供和安装工具、技能；工具缺失时按真实状态处理，不由执行层隐式安装 |

普通最终回复、typing、进度卡及统一交互卡属于已有 Channel 通信和呈现合同，不因本决定被删除。Agent 向其他会话发消息或交付文件则走工具调用；“Channel 投递最终回复”不能扩展为“Channel 接管任务副作用”。

## Context instructions

复用 octo.context-envelope/v3，不新增产物交付专用协议或执行器。IM 业务可在其选择的 extra.im item 中提供本轮交付指引；可信业务控制指令沿既有独立控制通道处理，不能将外部文件、历史内容或引用升权为控制指令。

例如，业务方可以表达以下任务要求，具体文本与 item 由业务方确定：

> 本任务需要交付报告文件。完成后使用已提供的 octo-cli 上传所需文件，并向本轮明确指定的会话发送文件消息。检查每个工具结果，报告成功与失败；已有有效文件地址时按工具合同直接使用。仅生成本地文件或给出本地路径不表示已交付，不要声称未发生的发送已成功。

这是表达方式示例，不是框架默认注入模板。Event 发起方决定 Context 的内容、顺序和发送时机；空模型 Context 继续有效。Host 不按 run 序号补发指令，Channel 不在任务结束后新造执行请求来补做交付。SDK 宿主接入仍使用 SDK；Agent 调用业务工具 octo-cli 不等于宿主通过 octo-runtime CLI 接入。

## 不稳定调用的修复位置

Agent 未调用、选错工具、参数不完整或漏做交付时，在业务方拥有的 Context instructions、提示词、技能和工具说明处对齐，并用实际工具调用结果验证。不得以模型不稳定为由，新增 Channel 扫描、自动补发、隐式重试或特殊 API 分支来替代工具调用。

实际 CLI、Provider 适配、身份传递或服务端违反既有合同时，修复最先违反合同的责任模块；提示词不替代真实缺陷修复，Channel 同样不得掩盖上游缺陷。现有权限、审批、传输重试与幂等合同继续有效，不为业务交付另造兜底流程。

必要执行基础设施与业务流程必须按合同区分：协议校验、权限/审批、原生工具执行与结果转发、取消/超时/资源清理属于各自既有责任；“模型可能不稳定”“旧 Gateway 曾有这段代码”不构成新增业务执行流程的必要性。确需新增基础设施处理时，在计划中写明无法由 Context/既有工具表达的实际合同缺口及责任模块，不能以必要为名恢复业务收尾执行器。

## 当前状态

F11 的跨会话发送与 F12 的显式文件、多文件、按任务要求交付产物，按当前 CLI 工具路径记为目标范围 100% 已覆盖，标删除线，无新增 Channel 开发。框架自动收集和投递 artifact 明确不采用，不是待实施或未来预留项。具体业务若需要提高自动交付稳定性，在其拥有的 Context/提示词中迭代，不因此降低既有工具能力覆盖或恢复旧流程。
