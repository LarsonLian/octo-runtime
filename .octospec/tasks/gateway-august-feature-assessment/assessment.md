# 评估口径

范围、版本与授权见[任务简报](brief.md)。本次已按最新授权逐项实施，真实进度、提交及 im-test 证据见[实施记录](implementation.md)。下方总表的“当前实现”已经更新；逐项 Review 章节保留原评审过程，其中“尚未实施/仅文档”是当时状态，不能覆盖当前实施记录。既有 journal 仍是历史证据，新验收不扩大原结论。

成本为相对评估：小=Channel 局部接线；中=涉及输入解析、资源预算或多个边界；大=新增 Provider、持久化或执行架构。不是工期承诺。P1/P2 为候选先后顺序，不表示本轮发现已证实的生产故障。

## 评分与目标覆盖口径

以统一协议为基础，分别评估“是否还需要新增工作”“所述路径能否落地”和“目标应选择多少业务范围”。统一协议提供共同的输入、Context、事件和执行合同，不要求所有渠道或 Provider 支持完全相同的业务能力，也不要求复制旧 Gateway 的架构。

| 指标 | 评分对象与含义 | 分档参考 |
| --- | --- | --- |
| 需求必要性（满分 100） | 在当前目标上继续新增、调整或补验本项的必要性。结合真实场景、现有缺口、统一协议的职责边界和已有决定；已覆盖的能力新增必要性可以很低，不表示该能力本身不重要 | 80–100 优先补齐/核实；60–79 有明确增量价值；30–59 条件成立再做；1–29 当前较低；0 无新增必要或与明确决定冲突 |
| 技术方案可执行性（满分 100） | 评估该格注明的实现路径能否沿当前统一协议和责任边界落地。已覆盖项评价复用路径；暂不纳入项仍评价其候选实现的成熟度，不把“不做”本身评为容易。考虑现有载体/接线、跨层改动、权限/资源约束及未验证依赖；不评价直接搬旧代码的难易 | 90–100 路径明确、现有机制可复用；70–89 可落地但有边界待验；40–69 方案或协议仍有明显缺口；1–39 尚无充分方案；0 所评旧目标违反当前硬约束 |
| 目标方案应覆盖比例 | 目标选择的业务范围，相对于该行列出的旧能力集合。100% 表示覆盖适用的业务目标，0% 表示本计划不纳入；每格同时写明保留/排除部分，避免把比例当作实现承诺 | 采用范围档位表达：0%、30%、50%、70%、100% 等；不是按代码量、提交数或任意子项等权计算的精确比例 |

评分是基于既有静态调查的工程判断，不是测试通过率、成功概率、工时估算或自动准入门槛。两项分数不取平均；可执行性高不代表需求必要，覆盖比例高不代表有新增开发任务。当前是否实现仍以“Runtime 当前实现”列为准，后续是否实施仍受任务范围约束。对旧持久化、逐会话目录和 capability 体系给 0 分，表示在当前目标合同内不采用，不表示编程上无法实现。

组合行需要按范围阅读：例如 F03 的既定目标仅为 Codex 独立图片，该范围已覆盖 100%；相对旧多引擎/多载体全集仍为部分覆盖，不以缺少明确分母的 30% 量化。F19 的 100% 指多 Bot 与隔离的业务目标，不要求每 Bot 一个 Worker。带“暂定”或“待决”的范围仍需核实业务合同，评分不替代决策。

覆盖度比较用户可观察的业务能力，不因旧方案特殊拼接、目标使用标准 Context 而扣减。协议承载形式与业务范围分别判断；统一协议能承载材料，不表示 Channel 已完成材料提取、准入与执行接线。F02 原 60% 将媒体理解和卡片操作混入文本阅读范围，口径不准确，修正为文本阅读目标覆盖 100%；当前尚未接通的实现状态保持不变。

2026-10-16 用户进一步明确：上述口径适用于全部后续项目，统一 Context 是目标方案；单纯提示词拼接形式不同不构成业务覆盖缺口。继续逐项评审时，先核对是否有材料、行为或执行链的真实差异，不自动将所有比例改为 100%，也不把 Context 能表达某项信息视为已经实现该能力。

## 删除线与逐项评审规则

整行删除线表示：按该行明确的业务目标，当前方案已覆盖，无需作为新功能继续评审。当前标记 F03、F06、F07、F08、F19、F33；F03 限已确定的 Codex 独立图片范围，F06 限 IM 在线展示，依据现有连接链、服务端/Web 源码及用户本地观察，不表示实现了 REST 循环。F07 限当前单版本 SaaS 的起始 typing 与卡片接替反馈。删除线不表示删除能力，也不表示本轮重新做过线上验收。F03 的真实 DM 图片和 F33 的合盖等未验场景仍沿原任务验收。

“目标方案应覆盖比例”是选择的范围，不能只因目标写了 100% 就划掉尚未接通的能力。删除线需有对应实现；待验范围必须保留说明。明确不采用旧设计的项目保留原结论，不重新推翻 Runtime 已有决定。

本次 F01/F02/F05/F18/F24/F26 的确认范围已接通，按目标标记删除线；F04/F09/F21 的具体未验范围和 F27 的已知重复风险仍明确保留。F28 延期，F31 文件策略单独实施；不把目标 100% 写成全部线上场景已验收。评分继续表达原需求价值及方案判断，不等于开发完成率；实施后剩余工作以当前实现列和实施记录为准。

### 文本构造约定草案

以下示例明确已选方案的承载方式；`reply` 名称、来源字段映射及预算在实施前定稿，不作为已经发布的新协议。示例内容为虚构数据。

```json
{
  "namespace": "extra.im",
  "name": "reply",
  "payload": {
    "text": "引用来源：张三（uid: user-example）\n引用正文：\n接口返回 401"
  }
}
```

Channel 根据本条报文提供的来源字段构造“引用来源”，保留有效正文的段落和内容；来源缺失时明确标注未知，不猜测身份。统一 renderer 完整输出 payload，模型结合普通 input 中的“这个怎么改”理解引用关系。JSON 序列化与上下文外框继续由现有 renderer 处理，Channel 不额外生成一套 Host 外框或 Provider 提示词。

| 当前容量与排序 | ImChannel 的 pending 统计当前 Bot 已接受的运行中与排队消息，合计最多 64；同一会话通过 Promise tail 串行，不同会话没有该串行屏障，不表示所有消息全局串行。结束后 finally 释放计数。不是每会话各 64，也不承诺单会话公平配额（R08） |
| 目标术语一：Bot 最大工作并发数 | 数值为 64。对一个 Bot，汇总其全部 session 当前已经取得执行槽位、开始处理且尚未结束的任务数，记为 W_bot；必须满足 W_bot<=64。同一 session 最多贡献 1。排队等待、已经结束及已拒收的消息不计入 W_bot。它不是 session 总数量上限，也不是宿主所有 Bot 共享的全局上限 |
| 工作中的生命周期 | 工作槽位从开始处理该任务、准备输入之前占用，至该任务执行与必要清理完成后释放；模型等待、工具执行、用户交互等待及本任务内部退避/重试仍占同一槽位。不得在每次 Provider 尝试结束时提前释放、再让同一任务多占槽位。卡片/普通文本投递另沿既有路径完成，不为已拒消息占工作槽位；执行期限仍按原合同从首次 invoke 起算 |
| 目标术语二：单 session 最大排队任务数 | 数值为 4。对该 Bot 下一个逻辑 session，统计已受理但尚未取得执行槽位、开始处理的普通任务数，记为 Q_session；必须满足 Q_session<=4。正在处理的 0 或 1 条任务不计入 Q_session。每个 session 单独计数、按接受顺序执行，不把其他群/话题/私聊的排队数累加进来。session 指渠道逻辑会话，不是当前发送者或 Provider 的 opaque sessionId |
| 边界示例与此前歧义纠正 | A 正在处理时，B/C/D/E 共 4 条可以排队；随后 F 到达，因该 session 队列已满而拒收。此前“A 工作、B/C/D 排队、E 拒收”对应的是排队上限 3 或未结束任务总数 4，与最新“排队任务数 4”不同；以用户最新命名及数值为准，不再混用两种口径。两个不同 session 各自可排队 4 条，同一 session 多个发送者仍共用这一队列 |
| 两种拒收与调度建议 | 新普通消息先完成既有授权与去重；对应 session 已排队 4 条时，拒收并报告会话排队已满。否则若 Bot 已有 64 条工作中任务，则拒收并报告 Bot 工作并发已满；两者同时触发时优先报告会话队列已满，便于稳定归因。已受理的排队任务继续保留，只有取得本 Bot 可用工作槽位后才能开始，不能在排队任务转工作时绕过 64。已拒收任务不自动重提。此建议不增加全局等待队列或跨 Bot 调度器，准入及槽位保留须原子更新 |
| 当前执行期限 | 默认 run_timeout_ms 为 86,400,000 ms，可显式缩短；现有长任务合同从本轮首次 invoke 发起计时，覆盖本任务后续尝试、退避及交互等待，不把每次重试重新算一天。排队与输入准备在此执行期限之外；不称作从消息到达起一天内必定完成，也不因此新增排队过期策略 |
| 已定位的反馈缺口 | enqueue 在 pending>=64 时只发 IM_INBOUND_CAPACITY_EXHAUSTED 诊断并返回 false；普通接收调用未把拒绝转换为回复，没有对应 AgentRun 或 final。源码只能证明这条客户端路径未发提示，不能据此声称已线上复现 Web 全部表现；平台自有已送达也不等于 Agent 已受理 |
| 已确认的用户反馈 | Bot 工作并发已满或单 session 排队已满而拒收时，立即尝试发送一张独立错误卡片和一条普通文本。主文案均为“当前智能体繁忙，请稍后再试”，卡片补充“本条消息未受理，尚未开始执行”，标题表达“暂未受理”；详情区分实际繁忙类型及公开错误码，不冒充正在排队或模型执行失败。不等待普通任务队列，不拼入其他任务正文或终态 |
| 两类统一公开错误码 | Bot 工作并发已满复用共享 FAILURE_CATALOG 的 OH-RUN-2003（runtime_capacity，action=retry_later），独立内部原因为 IM_BOT_WORK_CONCURRENCY_EXHAUSTED；单 session 排队已满须在同一共享目录新增不同的公开错误码，内部原因为 IM_SESSION_QUEUE_CAPACITY_EXHAUSTED。新增公开编号在实施前核对全局目录后分配，本轮不虚构已注册编号；不能只更换 reasonCode、仍让两类展示同一个公开码。两类均携带 diagnosticId、channel_admission 阶段及真实 Channel source，由共享分类入口映射，不建第二份 Channel 错误码表。保留旧 IM_INBOUND_CAPACITY_EXHAUSTED 为当前实现事实，不将它继续用于目标两类错误的模糊归因 |
| CanonicalEvent 卡片来源 | Channel 对本条被拒消息产生本地准入失败 CanonicalEvent run.failed，携带上述统一 FailureEnvelope，再经标准投影和既有卡片协议呈现。该事件是本地受理失败事实，不是 Provider 返回错误；不得调用 Host.invoke、分配真实 AgentRun 或伪造 run.started/accepted 来制造卡片。通知使用原始入站消息身份建立独立关联及幂等投递键，不借用正在执行任务的 runId 或卡片。此为待实施接线，不声称当前已有该事件路径 |
| 卡片与文本独立投递 | 卡片和普通文本均尝试发送到原连接、原频道/话题；卡片失败、模板不可用或预算不足不能阻止普通文案，卡片成功也不省略普通文本。两路使用各自稳定 effectKey，保留既有有界投递规则；不将卡片发送成功当作客户端已渲染或本条任务已受理，不自动重新提交被拒消息 |
| 通知边界 | 按入站消息身份幂等，重复帧不得重复通知；群内连续容量拒收的通知需限频、内存有界，具体窗口在实施时明确，卡片与文本作为同一次通知协调冷却，不让一条拒收意外重复发多套反馈。普通首条容量拒收尝试两路投递；洪泛冷却内可以抑制重复通知，网络失败如实记脱敏诊断，不承诺每条拒收两路均送达。关闭/取消、重复消息、身份不符及其他容量原因不复用这一文案 |
| 明确不扩展的范围 | 不搬旧 QPS 桶或跨 Bot/宿主全局调度器；本次小队列是用户新明确的本会话等待边界，不是照搬旧 Gateway 执行体系。不加排队超时/持久队列，不从拒收消息自动恢复执行，不改一天执行期限或 Provider 重试合同。取消、交互回答等控制不应排到被控制的长任务之后，继续遵循原有准入及生命周期合同 |
| 新增需求必要性 | 更新为 85/100：两类计数分别保护本 Bot 执行资源和单会话等待长度，避免单群的大量排队消耗其他 session 的工作机会，且准确反馈拒收原因。原 65 分仅针对补文案，不能代表新增两层容量模型的价值 |
| 技术方案可执行性 | 更新为 90/100：单会话串行、统一失败载体和卡片投影可复用，但必须调整本 Bot 调度计数及准入，验证队列转工作不会突破上限、取消/失败真实释放槽位、分类和边界顺序一致；不是将原常量 64 改为 4 即可。公开新码在共享目录分配，核心实现注释引用本方案。方案待实施，不把评估写成已实现事实 |
| 目标与当前覆盖 | 目标 100%：Bot 工作并发<=64、每 session 排队<=4且工作<=1、既定执行期限及两类卡片＋文本反馈。当前只有混合 Bot pending<=64、会话串行及执行期限；两层独立计数、两类公开错误和通知尚未覆盖，不标完成，不估算虚假的总体百分比。此前“Bot 未结束任务合计 64”只保留为源码现状，不再是目标定义 |
| 后续验收要求 | 单 session A 工作+B/C/D/E 排队可接收，F 拒收并展示会话排队公开码；其他 session 在 Bot 有工作槽位时仍可执行。64 个不同 session 各有一个工作中任务时，新普通任务因 Bot 工作并发满拒收，公开码 OH-RUN-2003；既有排队转工作不突破 64。验证同文案不同公开码、两层计数原子更新、取消/异常/关闭回收、无新模型调用的本地拒收事件、两路独立投递及消息幂等有界。实际群聊验收在 im-test 进行；无需真实启动 64 个付费模型任务来验证容量计数，可控执行与真实 IM 收发分别留证。本轮只记录计划，不运行测试或线上请求 |

### F26 定义与具体例子

本小节固定术语与计数口径。除明确标为“当前实现”的说明外，以下是待实施的目标方案，不是已有实现或线上验收结果。下文用 Bot M 表示一个 Bot，用 session S1/S2 表示它的不同逻辑会话，用 T1/T2 表示不同消息产生的普通任务，避免把 Bot、发送者、session 和任务混称为“一个”。

#### 对象与计数

| 名称 | 确切含义 | 不包含什么 |
| --- | --- | --- |
| Bot | 按现有 API、租户及认证身份作用域确定的一个渠道 Bot；同一 Bot 的全部群、话题和私聊 session 共享它的工作并发计数 | 不把所有 Bot、整个 Extra 或宿主当成同一个 Bot；不同 Bot 的计数分别维护 |
| 逻辑 session | 一个 Bot 在一个具体私聊、群或话题中的连续对话。多个已授权用户在同一群会话中向同一 Bot 提交任务，属于同一 session；不同群或不同话题分别计数 | 不按发送者再分一个队列，不把 Provider 返回的 opaque sessionId 当作队列归属。reset 的逻辑代次变化不得让尚未结束的旧任务退出原有计数或允许同频道并行 |
| 普通任务 | 一条已通过准入、可进入既有执行入口的普通消息所对应的一次业务任务；该任务内部的多次 Provider 尝试仍是同一个任务 | 同一消息的幂等重投不变成新任务；stop/cancel、交互回答、已拒消息及发送忙碌卡片不是新的普通执行任务 |
| 正在处理的任务数 W_session | 该 session 已取得工作槽位、开始输入准备且执行与必要清理尚未结束的任务数，只能为 0 或 1 | 不是 Provider API 当前正占 CPU 的数量；等待模型、工具、交互回答或本任务内部重试时仍为 1。仅发出取消请求但尚未收敛时也不能提前变为 0 |
| Bot 当前工作并发数 W_bot | 该 Bot 全部 session 的 W_session 之和，即 sum(W_session) | 排队任务、已结束任务、已拒消息不计入。64 不是 session 总数、用户人数、任务累计处理次数或其他 Bot 的并发数 |
| Bot 最大工作并发数 | W_bot 的上限为 64。开始一个任务前必须取得槽位，保证开始后的 W_bot<=64 | 不是“工作中+排队合计 64”。数值 32 是此前讨论过的候选，已被最新明确的 64 取代 |
| 当前排队任务数 Q_session | 该 session 中已经受理、但尚未取得工作槽位并开始处理的普通任务数 | 正在处理的 0 或 1 条不计入；其他 session 的排队任务不计入；未通过准入或已拒消息不计入 |
| 单 session 最大排队任务数 | 每个 session 的 Q_session 上限为 4；同一 session 的任务按受理顺序处理 | 4 不是该 session 工作与排队的总和。一个 session 可以同时有 1 条工作、4 条排队，共 5 条未结束任务 |
| 已受理与已拒收 | 已受理表示进入本 session 的工作或排队状态；已拒收表示这条消息没有进入两者。两者都不承诺模型最终成功 | 平台送达消息、发送繁忙提示成功，不等于任务已受理。被拒消息不因后续名额释放而自动重提 |

单个任务的目标计数变化如下；相邻步骤的计数更新与状态转移必须保持一致，不能因并发回调而重复占位：

| 状态变化 | Q_session | W_session / W_bot |
| --- | --- | --- |
| 新消息被接入等待队列 | 加 1 | 均不增加 |
| 队首任务取得槽位并开始处理 | 减 1 | W_session 从 0 变 1，W_bot 加 1 |
| 任务等待模型、工具、交互或内部退避 | 不变 | 保持占用，不释放也不再增加 |
| 执行及必要清理结束 | 不变 | W_session 从 1 变 0，W_bot 减 1 |
| 排队任务被真实移除或取消 | 减 1 | 不变；没有开始执行的任务不能释放工作槽位 |
| 新消息因容量不足被拒收 | 不变 | 不变；仅另行尝试繁忙卡片与文本 |

空闲 session 若可立即取得槽位，可以直接从新任务进入工作状态，不要求实际先建立队列项；结果仍必须是 Q_session=0、W_session=1、W_bot 加 1。卡片与普通文本投递不新增工作槽位；任务执行结束后的投递继续遵循同 session 原有顺序，不因此同时开始两条本 session 任务。

#### 准入条件与繁忙类型

先执行原有身份、群范围、mention、消息格式及幂等校验，再针对新普通任务检查容量。下表是本次具体调度建议，不新增每秒消息速率限制，不绕过宿主已有资源约束；该建议与当前代码的差异一并列入待实施方案。

| 条件，按此顺序判断 | 处理结果 | 展示的繁忙类型 |
| --- | --- | --- |
| Q_session 已为 4 | 拒收，不改变任何任务计数 | 单 session 排队已满；使用共享目录新增的独立公开错误码 |
| Q_session 小于 4，但 W_bot 已为 64 | 拒收，包括发送到已有工作中 session 的新普通消息；不在此时再扩大其等待队列 | Bot 工作并发已满；公开错误码 OH-RUN-2003 |
| 两者均未满，本 session 正在处理或已有更早的等待任务 | 新任务排到该 session 队尾，不超越先前受理任务 | 正常受理，无繁忙反馈 |
| 两者均未满，本 session 无工作或等待任务 | 原子取得工作槽位并开始处理；同时到达的其他消息按更新后的计数重新判断 | 正常受理，无繁忙反馈 |

两种繁忙同时成立时，按第一条报告“单 session 排队已满”，不能随机返回不同码。此前已受理的排队任务不因 Bot 后来达到 64 而被清退；它们须等待本 session 前一任务结束及 Bot 工作槽位可用，再转入工作。具体跨 session 就绪调度沿插件内部最小实现处理，不承诺不同 session 的严格先来先执行，也不新增跨 Bot 全局协调接口。

#### 可直接核对的例子

以下例子彼此独立。除特别说明外，消息均已授权且通过普通准入，未触发通知冷却，其他宿主资源也可用。每条拒收消息均尝试卡片+文本“当前智能体繁忙，请稍后再试”；卡片说明“本条消息未受理，尚未开始执行”，详情显示相应繁忙类型、不同公开码及 diagnosticId。

| 编号 | 发生前的状态及新消息 | 明确结果 |
| --- | --- | --- |
| F26-E01 空闲会话 | Bot M 的 W_bot=0；S1 没有任务，T1 到达 | T1 开始处理；W_bot=1、W_S1=1、Q_S1=0。不是占用 1 个排队名额 |
| F26-E02 同群不同人 | S1 中用户甲的 T1 正在处理；用户乙、丙、丁、戊依次提交 T2/T3/T4/T5；Bot 其他工作任务不足以使 W_bot 达到 64 | 四条均在 S1 排队；W_S1=1、Q_S1=4。同群四个不同发送者不会各建一条独立工作链 |
| F26-E03 第六条消息 | 延续 E02，用户己向 S1 提交 T6 | 拒收 T6，提示单 session 排队已满；T1 继续，T2/T3/T4/T5 保留，计数不变。不是 T5 就拒收 |
| F26-E04 其他群独立 | S1 为 1 条工作+4 条排队，Bot M 的 W_bot=1；另一个群 S2 收到 T7 | S2 可开始处理 T7；W_bot=2、Q_S1=4、Q_S2=0。S1 的排队满不占用 S2 的队列名额 |
| F26-E05 不能混加总量 | 同一 Bot 的 20 个 session，各有 1 条工作+4 条排队 | W_bot=20，每个 Q_session=4，共有 100 条未结束任务。此状态符合两层目标；不能因 100 超过旧 Bot pending=64 而认定超限 |
| F26-E06 Bot 工作满 | Bot M 的 64 个 session 各有 1 条工作任务；空闲 S65 收到新任务 | 因 W_bot=64 拒收，卡片显示 Bot 工作并发已满、OH-RUN-2003；S65 队列原本为空也不能据此绕过 Bot 并发检查 |
| F26-E07 已有群也遇到 Bot 满 | W_bot=64；S1 仍有工作任务，但 Q_S1=2；S1 又收到新普通消息 | 按本次准入建议拒收，报告 Bot 工作并发已满，而不是会话排队已满；已有两条排队任务不清退 |
| F26-E08 两种都满 | W_bot=64，Q_S1=4；S1 又收到新任务 | 两项条件均成立，固定优先报告单 session 排队已满。主文案与 E06 相同，但公开码不同 |
| F26-E09 释放并接续 | S1 的 T1 工作、T2/T3/T4/T5 排队；T1 结束并完成必要清理 | 已实现原子接续：本 session 有排队时将原槽位直接交给 T2，不先暴露给其他 session；稳定状态仍为 W_S1=1，Q_S1 从 4 变 3。队列清空才释放 Bot 工作槽位，避免已接纳任务因竞争丢失工作资格 |
| F26-E10 工具等待不释放 | S1 的 T1 在等工具结果或用户交互，T2 已排队 | T1 仍占 1 个工作槽位，T2 不得启动；不能把“当前没输出”误判为 session 空闲 |

### F27 无 ACK 重试与 REST 未知结果卡片

用户确认“最多重试 3 次”指首次发送之外的额外尝试，最多发送 4 次；1/5/10 秒是上一次尝试未确认后、下一次发送前的等待时间，不是 ACK 超时，也不是从首次发送起算的绝对时点。ACK 是服务端发送确认，不是用户已读。

| 尝试 | 开始条件 | 等待 ACK |
| --- | --- | --- |
| 首次发送 | 正常投递 | 沿当前单次最多 15 秒 |
| 重试 1 | 首次仍未确认后等待 1 秒 | 最多 15 秒 |
| 重试 2 | 重试 1 仍未确认后等待 5 秒 | 最多 15 秒 |
| 重试 3 | 重试 2 仍未确认后等待 10 秒 | 最多 15 秒 |

四次均用满 ACK 等待时，发送阶段约为 4×15+1+5+10=76 秒，不包含模型执行和后续 REST 卡片耗时；取消、卸载或投递剩余期限不足时提前停止，重试不得刷新外层期限。串行尝试同一条消息，不并行补发；保持相同正文、地址和 clientMsgNo/effectKey，协议序号仍按 WS 合同生成。稳定消息标识不等同于服务端已保证去重：用户已选择有限重发，仍可能重复显示回复，需要核对服务端去重合同并报告实际能力。暂时无连接时沿现有连接状态机和投递预算处理，不另起连接恢复流程。此策略仅改本项 WS 回复，不机械扩大到所有 REST、typing 或 Agent 业务工具。

投递操作在有效期内把各次尝试关联到同一逻辑消息：收到可关联的任一次成功 ACK，就停止后续重试及尚未发出的未知结果通知；不能因该次尝试早先超时而忽略其迟到成功 ACK。某次发送结果未知后，后一次本地失败或拒绝也不能反证前一次肯定没有送达。没有成功确认且至少一次发送结果未知时，最终保留 unknown。

重试耗尽后，独立通过 REST 尝试发送一张投递错误卡片到原会话。此卡片是一个逻辑通知，不是再发原回复，也不是再次执行任务：

- 标题：**回复送达结果未知**。
- 建议文案：**回复已尝试发送，但未收到消息服务的确认，可能已送达。请先检查聊天记录，避免重复提交任务。** 不写“任务执行失败”或“消息肯定未送达”，不附带强制重跑 Agent 的操作。
- 共享错误目录新增独立公开错误码，区别于 F26 两类繁忙及 Provider 执行失败；公开编号实施前统一分配，本轮不虚构已注册编号。内部原因沿 IM_DELIVERY_UNKNOWN，阶段为 channel_delivery，带 diagnosticId 及脱敏逻辑消息关联信息；不建立第二套 Channel 错误码表。
- 卡片通过通用事件/错误投影生成，REST 仅负责发送；执行终态与投递终态分开。不得把已完成的 AgentRun 改写为 run.failed，也不得旁路 CanonicalEvent 手写另一套卡片业务。实施时核对现有通用事件是否能表达投递诊断，不足时补最小通用合同和投影，不假定当前已有专用投递事件。
- 同一逻辑回复只产生一张未知结果通知，使用区别于原回复的稳定 effectKey；REST 发送沿既有终态卡片最多 3 次投递和取消预算，卡片失败只保留诊断，不再产生“错误卡片发送失败”的另一张卡片。REST 与 WS 可能同时不可用，不能承诺通知必达。
- 主动取消或 Extra 卸载后停止发送，不为已取消的任务或已卸载插件补发此卡片。本轮不新增持久投递账本、跨重启自动补发或宿主对插件内部连接的控制。

实施验收覆盖：明确拒绝不再落入 unknown；永久拒绝只尝试一次；无 ACK 的首次加 3 次及 1/5/10 秒间隔；相同消息标识及迟到成功 ACK 停止重试；未知不被后续拒绝错误覆盖；取消终止等待；REST 仅一张逻辑错误卡片、专用公开码及失败不递归；发送失败不触发模型/工具重放。核对服务端 ACK 原因及去重合同，并在获准实施后使用线上测试环境验证 ACK 丢失与 REST 降级场景。这些是后续验收目标，不是本轮测试结果。本项后还剩 F28–F32 共 5 项。

## 逐项 Review：F29 权限分档与工具网关

主结论：**现有“设备执行内核 + Extra 插件 + 外部工具”已把职责与权限划分清楚，满足 F29 目标架构。** 其收益是执行内核可跨业务复用、业务工具和 Provider 分别演进、避免重复策略与状态、故障可以按真实责任定位。旧分档将准入、原生权限和业务代理集中装配的教训，以及防止后续恢复耦合的评审要求，已记入[架构决策](../../journal/shared/2026-10-16-kernel-extra-tool-boundary.md)和[强制规则](../../rules/architecture.md#设备执行内核extra-与外部工具的职责权限边界)。这不是单纯不迁移旧功能，而是保留已满足目标且责任清晰的架构。

状态：用户确认保留现有职责划分，本项架构评审已过项，不新增改造。按接入准入、工具调用身份、AgentRun 执行权限三类目标覆盖 100%、标删除线；旧耦合控制体系明确排除，不能把“未复制旧体系”写成缺口。本轮仅文档，不改权限、审批默认值、代码或配置。

用户意见：F29 将多个不同问题杂糅在一起，容易误导为 Channel 缺少统一权限中心。Extra 接入层做准入是其正当职责；ChannelGateway 已提供 Bot 身份授权，CLI/MCP 工具在相应执行环境内按配置的 bf_token 调用；是否允许操作本地文件等属于 AgentRun 统一执行协议的权限/审批策略，包含 full_access，不应回到 Channel 另起权限分档。

工程评估：同意上述责任划分。真实判断对象分别是“谁能触发”“以谁的工具身份调用”“这次执行允许做什么”；三者互相独立，不需要一个 Gateway 档位统一推导。旧方案在同一层组合这些约束与业务代理，增加了配置和 Provider 差异的耦合；新方案让校验与副作用留在能实际执行其合同的组件，排障时也能区分准入拒绝、凭据/资源拒绝与执行权限拒绝。不能把 old tier/broker 不存在当成新架构授权未完成，也不能将 F29 写成一个待建设的混合权限功能。

| 权限维度 | 唯一责任与当前路径 | 不应混同 |
| --- | --- | --- |
| 接入准入 | Extra/Channel 校验真实发送者、Space、允许名单、群范围和 @ 条件，决定本消息是否可启动执行 | 获准触发不等于得到发送者本人的全部业务权限，也不决定 Provider 文件权限 |

### 当前改造评估

结论：有明确的架构价值，建议纳入后续方案。SDK 是主要接入方式，宿主显式装配日志能力；Extra 经加载器注入的日志函数记录业务事件；执行内核记录通用调用生命周期。格式和受管文件策略共用，业务含义各归其主。ctx 是 ExtraContext 执行环境，不是发给模型的 Context v3，不改变 Run=7 或 Context=v3 协议。

| 改造点 | 具体收益 | 责任与限制 |
| --- | --- | --- |
| 两类日志按责任分开 | 查执行问题看内核，查触发/连接/投递看 Extra；减少从启动方式和文件名前缀猜归属 | 内核不理解 Bot 业务；Extra 不接管执行内核，也不管理文件 |
| ExtraContext 注入 log 函数 | 插件只提交事件和元数据，测试可注入替身；不 import 宿主 logger，不读日志目录，不直接写文件 | 建议 ctx.log(level, event, data)，加载器绑定真实 extra_type；不增加插件业务控制 RPC 或内部 manager 接口 |
| 同一结构化格式 | SDK、Runtime CLI 和不同 Extra 可按同一字段检索，后续宿主接日志平台无需解析各自文本 | 建议公共字段 time、level、source、event、extra_type（仅 Extra）、data；extra_type 来自声明名称，不让 data 覆盖公共来源 |

#### 日志内容边界（用户已明确，待实施）

本方案的内核日志与 Extra 业务日志均遵守以下范围；ctx.log 的 data 不是任意请求对象的转储入口。

| 对象 | 允许记录 | 不记录 |
| --- | --- | --- |
| 调用生命周期 | 已有请求/Run/会话标识、事件名、时间、耗时、状态和稳定错误码 | 请求或回复正文、原始协议帧，以及可能夹带正文的任意错误对象或错误消息 |
| Adapter Context | 显式白名单内的非敏感执行选择摘要，例如 Adapter 类型、模型名称；具体白名单在实现方案中列明 | 完整 Adapter Context、环境变量值、凭据、任意 Provider 配置对象；“允许摘要”不表示必须打印全部配置 |
| 核心 input | 本轮核心输入项数；有明确输入类型时可按类型分别计数 | 文本、图片或文件内容、地址、正文预览、截断片段或内容哈希 |
| 其他 Context | 本轮除 Adapter 外的 Context item 总数；如按类型计数，只用已知协议分类 | instructions、extra.im 等 item 的内容，以及引用、材料、完整 envelope 或其预览/截断副本 |

“数量”指结构中的项数，不是字符数、字节数或 Token 数。例如，本轮 1 个文本输入、1 个图片输入，以及 3 个非 Adapter Context item，可记录核心输入 2 项（文本 1、图片 1）、其他 Context 3 项。一个 item 内有多段文字仍计 1 项；不拆正文计算段数。仅统计本轮实际收到的数据，不读取历史、补齐 Context 或调用模型估算 Token；统计字段只是日志元数据，不修改执行协议。

这条边界由用户明确，其他候选接口、文件名和轮转口径仍待评审。收益是减少日志体积、序列化开销和正文暴露，并让日志依赖稳定的执行元数据，避免与各业务 Context 的正文结构耦合。未来验收需确认正常、失败及 Extra 日志均不泄露正文或完整配置；本轮仅记录约束，未修改日志实现。

#### 现有链路的评价

- service-out/err 是 Runtime CLI launcher 收集 daemon stdout/stderr；embedded-runtime 是 SDK supervisor 收集 runner stdout/stderr。它们是不同启动入口的外层输出收集，角色相近，但不是两份同样的执行内核事件日志。后者确实接着输出管道；默认启动诊断较少，正常运行时可以很安静，不能推断它完全不工作。
- 当前小时文件名和清理器已经实现轮转保留，不是“文件名带小时就不能轮转”。用户提议的收益是活动路径稳定、文件结构易读，并统一写入政策。
- 旧 adapter-host debug 包含协议元数据及内核诊断，playboard 则显示本次请求的输出；两者并非完全等价。推荐将有用的开始/结束/错误信息归入新内核日志后，停止维护旧独立 debug 文件和逐帧 trace，而不是因 playboard 存在就删除所有内核排障信息。
- 建议不再把 SDK/launcher 原始输出各自创建为产品日志类别。退出码、启动前异常、Provider stderr 的必要诊断仍需保留可观察路径；不能为了“两类文件”而吞错。不能把任意子进程原始输出直接当作结构化日志或自动脱敏材料。

#### 具体接口与轮转建议的待定项

1. 路径使用宿主提供的绝对 logs 目录，不拼接 `~/{OCTO_RUNTIME_HOME}`；Home 可能本来就是绝对路径。宿主可选择 `<其 Home>/logs`，SDK 不自行推导或另建一个目录。
2. “两类日志”指内核执行与 Extra 业务两类责任，不表示只能有两个物理文件。建议内核使用固定 info/err 活动文件，Extra 使用 `extras/<extra_type>.log` 并在记录中保留 level；具体 basename、warn 归属和是否拆 Extra 错误文件待定。level 不等于进程 stdout/stderr，不能将所有 console.error 信息都认定为业务错误。
3. 建议“保留最近 3 个”明确为每个文件序列总共 3 个（当前活动文件 + 最近 2 个已轮转文件）。这与“当前及前两个小时桶”和“保留精确 180 分钟”不是同一口径，须在后续方案中选定；本轮不擅自替用户确定。沿用单文件最多 100 MiB 作为容量建议，不因改名恢复无限追加。
4. invoke 接收、内核实际开始、真实终态和 RPC 流结束分别记录；接纳不等于开始，流结束不等于成功。取消请求与取消完成也分开；真实结果未知时保留 unknown。Extra 的 agent_run 触发事件与内核开始事件通过相同标识关联，不重复声称两次执行。
5. 同一文件必须明确写入归属及跨进程轮转协调；复用已有有界互斥/容量能力，不能让多个进程独立 rename 同一活动文件。写入失败、慢磁盘或序列化失败不得影响 Agent 执行，也不创建无限队列。

本次已确认纳入改造方向，不宣称上述具体接口名、文件名或保留口径已确认。新接口需同步公开 Extra 类型、加载器、SDK/Runtime CLI 接线和插件调用点；未来实现必须验证关闭零落盘、显式目录、轮转/容量/并发、真实成功/拒绝/取消/未知状态及卸载清理。涉及真实执行时使用 im-test；本轮未运行。

### 此前最小接线调查（历史建议，已被上述改造评估取代）

通俗解释：Bot 出问题时，需要知道“哪个 Bot、哪次执行、哪个环节出错”。这不要求每个 Bot 都有一个日志文件，也不要求执行内核理解 Bot 业务。

旧提交 d11b396 的目标是将独立 Bot 进程的输出，从按 runtime 命名的共享临时文件改为 `bots/<botUid>/logs/slice.log`，避免不同 Bot 输出混在一起。该方案依赖旧每 Bot 进程和受管目录模型，不是新架构必须复制的能力；所核对的 slice-log 模块本身是固定文件追加，没有当前小时分桶容量合同，不能直接作为替代实现。

| --- | --- | --- |
| 内核自身诊断 | Host debug 及协议 trace 有实际输出路径；trace 按合同不保存正文、Context、图片和可信环境 | 保留通用执行诊断，不加入 Bot 日志目录或业务正文存储 |
| 受管进程输出容量 | HourlyLogWriter 用于 Host debug、SDK 子进程和 Runtime CLI 托管服务；每类别保留当前及前两个 UTC 小时桶，单文件最多 100 MiB | 保留既有容量合同；它不是所有宿主日志的统一存储要求，也不会自动脱敏 Provider/第三方程序写出的任意文本 |

状态快照和执行卡片能够展示部分失败，但不等于完整诊断历史；普通 console 输出被宿主收集，也不会自动补出没有发出的诊断。反过来，本项不要求新建持久化诊断账本、聊天历史库或跨 Bot 全局控制状态。

### 具体还差什么

缺的是诊断发出端接线，不是日志文件或存储系统。默认入口没有接回调，以下代码路径已经产生的诊断不能经该回调进入现有日志；这不表示它们在其他状态、卡片或输出中绝无体现。

| 已有诊断场景 | 现有错误码举例 | 接线后能解释的问题 |
| --- | --- | --- |
| 入站容量拒绝 | IM_INBOUND_CAPACITY_EXHAUSTED | 消息为何没有进入任务处理；不把接线误写成已实现 F26 新的两类容量错误码 |
| Context 准备或本轮处理失败 | IM_CONTEXT_PREPARATION_FAILED、IM_TURN_FAILED | 请求在哪个准备/处理环节停止；不记录材料或正文 |
| 用户控制请求失败 | IM_INTERACTION_RESPONSE_FAILED、IM_RESET_REPLY_FAILED、IM_RESET_FAILED、IM_CANCEL_FAILED | 交互回答、重置回复或取消处理中的失败分支；错误码按实际调用点解释，不宣称能恢复所有底层原因 |
| 投递或卡片呈现失败 | IM_DELIVERY_FAILED、IM_PRESENTATION_FAILED，以及呈现层传入的诊断码 | 执行与回复/呈现故障可分开定位；具体码仍由现有责任模块产生 |
| 执行流结果未知或任务停止 | IM_EXECUTION_RESULT_UNKNOWN、task.stopReason | 记录结果未知或已有停止原因，不伪造执行成功或模型失败 |

最小建议方案已经明确：在现有函数式 Extra 和保留的对象式模块装配中接入 onDiagnostic，将错误 code、endpointId 和已有的可选 runId 输出为一条结构化 console.warn/stderr 诊断。SDK 子进程输出和 Runtime CLI 受管输出已有对应采集路径，其他宿主按自己的现有输出机制处理。无 runId 的前置错误只记录已有身份，不编造 Run，也不要求为本项修改所有诊断调用点。传输层经现有回调上报的诊断沿同一出口。

只输出上述元数据，不输出原始 Error、完整配置、Token、聊天正文或 Context。日志保存位置、检索和平台接入归宿主；不新增日志文件、ExtraContext logger、业务 RPC、插件内部控制接口或 Channel 日志存储配置。现有日志容量及诊断不影响执行的合同继续有效。该方案只补齐已有诊断的发出，不承诺全链逐事件追踪或旧 slice.log 文本逐条等价。
