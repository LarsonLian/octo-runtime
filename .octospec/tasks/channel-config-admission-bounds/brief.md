# Channel 配置操作队列的准入与容量限制

## 状态与问题说明

状态：已实施，针对性回归及 im-test 建联/卸载通过；全仓检查随四批交付统一记录。单个 channel-gateway Extra 实例最多配置 64 个 Bot，不是整台设备的上限。实现及验证见[交付记录](../../journal/shared/2026-10-16-runtime-config-bounds-delivery.md)。

这是“更改 Bot 配置”的队列，不是收到聊天消息后的任务队列。举例：第一次 upsert 还在等待连接，调用者又发来一千份 upsert；[manager](../../../packages/octo-runtime-extra-channel-gateway/src/lifecycle/manager.ts) 立即 structuredClone 每份配置，再通过一个 Promise 链串行处理。16 个 Bot 的端点限制只在操作实际开始后才检查，不能限制排队的一千份配置。已复现一千份约 32 KB 配置使 GC 后堆增加约 33.2 MB，即使只有一个活动端点。

审查时 [Extra](../../../packages/octo-runtime-extra-channel-gateway/src/extra.ts) 最多接收 16 个 Bot，逐个 await 启动，常规路径风险较低；本次已将 Extra 加载校验与 manager 活动端点上限统一调整为 64。导出的 manager 与 [保留的 daemon module](../../../packages/octo-runtime-extra-channel-gateway/src/daemon-module.ts) 的 handle(upsert) 可并发提交，也受同一队列准入限制。

## 架构边界

宿主更改配置仍按“卸载 Extra -> 保存完整配置 -> 重新加载”编排，见 [Extra 合同](../../rules/extras.md)。本专项不给 Extra 新增 updateConfig RPC、自动合并配置、debounce 后写覆盖或无限重试；用户消息的 64 条在途限制与此队列独立。

## 首版固定上限

| 项目 | 建议值与口径 |
| --- | --- |
| Bot 数量 | 用户已确认：单个 Extra 实例最多 64 个 Bot；对应 manager 最多 64 个活动端点 |
| 管理操作总数 | 工程建议：每个 manager 最多 64 个，包含正在执行与等待中的 upsert/remove；与 Bot 数量分别计数 |
| 单份配置 | UTF-8 JSON 最多 256 KiB，包含 Context 和凭据字段的字节但不输出其内容 |
| 配置快照合计 | 不另设 1 MiB 限制；64 个操作乘单份 256 KiB，自然上界为 16 MiB。活动端点稳定配置另受 64 端点和单份限制，也是最多 16 MiB；这些不是整个进程的内存上限 |
| 同一 Bot | 每份已接纳操作按原顺序执行，不静默替换、不合并不同调用方 Promise |
| 超限 | 立即拒绝；操作数超限为 IM_CONFIG_QUEUE_CAPACITY_EXHAUSTED，单份超限为 IM_CONFIG_TOO_LARGE；活动端点超限沿用 IM_ENDPOINT_CAPACITY_EXHAUSTED |
| 其他失败 | 无效配置和 manager 已关闭按原错误拒绝，不先排队再发现 |

64 个 Bot 是用户决定；64 个管理操作与单份 256 KiB 是首版工程建议。撤回之前 16 个操作、合计 1 MiB 的偏紧建议，使用操作数和单份大小两个简单边界即可，不再维护独立累计字节准入。等于上限允许，再接纳导致大于上限时拒绝。64 个合法 Bot 的默认串行加载必须可用，不新增可配置限流器。

## 准入与执行过程

1. 入口先检查 manager 是否关闭及基本配置合法性。统一计算 JSON 大小并校验单份上限；使用有界的大小检查，不能为了拒绝一个超大配置先克隆完整对象或生成无限临时字符串。非法、循环引用或不可序列化对象立即拒绝。
2. 在同一个同步准入段检查并预占操作名额，最后只复制一次接受的配置。超限操作不得创建持有完整配置的 Promise 闭包；复制失败归还名额。不新增独立累计字节准入计数器。
3. 已接纳操作继续使用原有串行顺序。upsert 在替换时先关闭旧连接，再启动新连接；不得因为这次限额改成并行建联。端点数在实际执行时仍校验，不能把操作容量当作端点授权。
4. 成功、鉴权失败、初始化抛错、remove 失败及 abort 都在 finally 释放对应操作名额和配置引用。一次失败不能占住未来额度，也不能造成减两次或负数。
5. close 不进入普通操作队列，先禁止准入并 abort 在途初始化，再按原合同等待操作结束与资源清理。即使队列满也能关闭；已接纳但未执行的操作受控拒绝并释放快照。关闭后没有悬挂 Promise 或自动重新加载。
6. 超限反馈交给调用方，不在 manager 后台重试，不让普通聊天因此重跑。无凭据/正文进入日志或状态；需要诊断时只输出有界的操作数量与字节数，不新增历史账本。

不优先做“同 Bot 只保留最后一次配置”：这会改变先前每个 upsert 的成功/失败语义，还需要取消、覆盖和调用方通知规则。固定容量直接拒绝已足以关闭本次风险，合并更新没有当前业务需求。

## 验收矩阵

| 场景 | 必须观察的结果 |
| --- | --- |
| 正常顺序加载 64 个 Bot | Extra 与 manager 均接受，无并行重复连接；第 65 个超出实例上限，按各入口合同报告容量错误 |
| 首次连接阻塞，再提交大量配置 | 最多保留 64 个操作；之后立即拒绝，拒绝数量增长不带来快照堆增长；不能因额外的 1 MiB 门槛提前拒绝 |
| 单份 256 KiB 前后及操作数 64/65 | 精确边界、错误码和计数符合合同，统计含活动操作 |
| 连续提交同一 Bot 配置 | 已接纳项依次执行；没有静默覆盖或新的无限 per-Bot 等待表 |
| 验证失败、复制失败、启动/关闭失败 | 容量归还一次；后续合法操作仍可接纳 |
| 队列满时 close 或宿主 abort | 不等待获得排队名额才取消；所有 Promise 结算，快照和计数释放 |
| 一个失败 Bot 和其他合法 Bot | 错误不扩散为整个 manager 泄漏，仍按原串行及清理合同处理 |
| 超大或不可序列化的直接 SDK 对象 | 在复制前拒绝；无凭据输出，无无限大小临时 JSON |

优先扩展现有 IM lifecycle/disposal 测试，并在专用测试对象中注入可取消的慢初始化。开发先 build 后执行针对性 Node test，最终运行工程检查及全量回归。不要用真实线上无限提交制造风险；im-test 只使用有界样本，本地 GC 压测负责证明容量。
