# Extra 函数式改造难度、风险与可执行性评分

2026-10-17 实施说明：以下 86/100 是实施前准备度，保留为历史判断。本轮已完成共享 loader、CLI 三个 Extra、两渠道动态 Context 和指令前置修复，并验证内存和 im-test/Codex。用户明确暂不改 SDK 接入，因此 SDK HostApp 装配 gap 留待后续；真实 WeCom 及全 Provider 会话矩阵也不宣称完成。当前交付事实见[记录](../../journal/shared/2026-10-17-extra-initializer-delivery.md)，不以重新打分替代测试结果。

## 结论与评分口径

按当前[详细设计](brief.md)，整体开发准备度 **86/100**；技术上可实现，整体难度中等偏高。纯合并和函数签名难度低，SDK 同进程装配与取消/清理正确性是主要工作。不考虑旧接口兼容降低了分支数，但不会消除多入口同步更新和实际生命周期验证的成本。

分数是基于已核对代码的工程判断，用于表示“方案距离可以直接实现并验收还差多少”，不是代码完成比例、测试覆盖率、成功概率或技术写作合规分。90 以上表示输入、行为与验收明确，仍要实现；70–89 表示存在待验证接线；70 以下表示关键方案仍缺失。权重只是本次评估口径。

## 2026-10-17 评审后的 gap 分类

用户已同意 SDK 同进程装配、两阶段初始化及有界内存方向，确认业务函数依赖与模型执行端口的区别。宿主 load/unload/整体停止由用户提出初步想法并要求评估；[生命周期评估](design.md#生命周期分工的工程评估)建议采用“宿主决定通知、SDK 有界协调、插件内部清理”，明确取消范围、停止顺序及失败行为。不能将本次工程建议记成用户逐项批准的实现细节。86 分保留为上次源码评估基线，未凭讨论本身增加实现或验证分数。

剩余工作分为：

- 接口实现：把已确认的两阶段签名和 SDK 本地装配接入代码。
- 内部模型端口接线：SDK 复用既有 invoke/cancel/respondInteraction，核对 invocationId；不是要求业务方注入模型执行实现。
- 生命周期实现：宿主通知单个 load/unload 或整体 stop，SDK 协调，Extra 自行清理内部资源。
- 运行证据：同步/异步回调、取消、晚结果和内存测试，证明没有随历史消息/重载次数增长的新增引用。
- 原有缺陷依赖：统一准备及 instructions 简化任务，独立于本次函数注入接口。

## 最值得优先处理的难点

### 1. 函数究竟在哪个进程执行

现有 SDK serialize extras 到 runner，外部闭包不存在于那里。这是明确事实，不是要求设计函数 RPC。推荐改成 SDK 在 HostApp Node 组合层运行完整 Extra，复用原执行内核；CLI 在自己的 daemon 层组装。若只改类型和文档，不改装配，用户仍无法实际注入函数。

M0 要做最小真实接线：宿主闭包读内存及受控 IO，实际接到 Provider fake 输入；取消/交互命中同一个 invocation；停止时先停 Extra。然后在仓外安装包中重复。M0 未通过不能进入“SDK 可用”宣称。

### 2. 超时、取消与内存是否真的退出

Promise.race 只改变当前等待者。若超时就释放槽并开新调用，旧 IO 不退出时会越来越多。方案明确占用到实际 settle，并在卸载失败时阻止重载叠加。外部必须合作取消；同步死循环无法在同线程强制中止。此限制写成真实边界，不以函数式名义承诺消除。

M0/M2 还需选定复用的 JSON 预算检查实现，确保巨型返回值不会先经过全量 stringify/clone；资源合同已有目标，具体工具接线尚未验证，因此该模块未给 90 以上。

### 3. 接到 Context 不等于 system 已更新

动态 ordinary extra 每轮可传递；新系统指令对已有 Provider session 的生效按其原生合同处理。固定人设示例与动态 instructions 整项替换不能同时暗中保留。方案选择维持整项替换，业务回调要覆盖时自己给完整指令；产品如要求身份不可替换，需调整该业务覆盖规则。

已有[统一准备修复任务](../unify-execution-and-simplify-instructions/brief.md)必须交付，否则控制项仍可能在 Provider 启动前被错误 resolver 拒绝。这是端到端前置缺陷，不是动态函数设计本身的阻碍。

## 改造风险及可观察的防线

| 风险 | 严重度 | 防线与通过依据 |
| --- | --- | --- |
| 只 await 外层，未调用内层 | 高 | 缺 initializer 明确失败；连接资源及业务状态确实已初始化后才 loaded |
| SDK 重复装配 Extra，造成双连接 | 高 | 本地 loader 为唯一 SDK 归属；daemon 不重复加载，真实只建立一组连接 |
| runId 与 invocationId 误接，取消错对象 | 高 | 独立端口检查；两同时运行任务中取消/交互只命中目标 |
| 超时后旧回调持续积累 | 高 | 原操作实际 settle 前占槽；超额报忙、不新增等待队列，挂起测试稳定在上限 |
| 卸载后迟到结果回写 | 高 | abort/代次校验、晚结果丢弃，清理失败阻止覆盖加载 |
| 异步返回巨大对象 | 高 | 外部受限 IO，入口预算检查先于复制与序列化；堆数据验证 |
| 合并丢静态项、乱序、深合并 | 中 | 纯函数案例覆盖替换/追加/空列表/同源重复，输入不变 |
| instructions 被覆盖而丢默认人设 | 中 | 明确整项替换，完整回调示例，不能偷偷拼回默认 |
| 默认配置漏同步，旧消费者仍导入旧接口 | 中 | 统一删除旧签名、公开包仓外编译、三内置插件和文档盘点 |
| 日志泄露 config/动态正文 | 高 | 仅稳定错误码、项数、耗时、在途计数；不记录正文或原始错误 |

## 建议的实现顺序

1. 先做 M0：用最小插件证明本地闭包装配与执行端口，覆盖同步/异步返回和 unload。不先铺开两渠道业务改动。
2. 完成两阶段 loader 及三内置入口的一次性迁移，保住原清理合同，删除旧入口及远端 SDK Extra 装配。
3. 独立完成小型无状态合并函数，再把动态回调接到两个 Channel 的正确准备位置。只暴露 loadContexts。
4. 补资源准入、真正退出计数和预算检查，做挂起/迟到/超大对象及堆回归。
5. 与已有准备及 instructions 简化任务合流，更新默认正文和所有完整配置示例。
6. 仓外包和真实 im-test 验收；WeCom 缺真实凭据时保留未验项，不将 Octo 结果替代 WeCom 结果。

不建议把 Context v3 其他精简候选、所有 Provider system 热更新或通用依赖注入体系一起塞入本任务。它们会扩大合同和验收面，与本次函数式入口的核心目标无直接依赖。

M0 通过后，SDK 装配若升至 90，整体可执行性约 90；预算工具和真实端口证据齐备后再评估。没有实际验证前不提升为 100，也不把本轮文档检查当作运行时证据。
