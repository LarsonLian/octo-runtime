# Extra 动态加载的内存边界与验证

状态：本轮实现了有界在途、超时不释放未结束名额、取消、迟到结果丢弃和 5 秒有界卸载。强制 GC 的一万次动态加载、两渠道各一万会话、重复装卸及不合作 Promise 回归通过，具体数值和适用范围见[交付记录](../../journal/shared/2026-10-17-extra-initializer-delivery.md)。SDK 同进程装配的内存回归仍延期。与[接口设计](design.md)一起使用。

2026-10-17 用户确认采用不保存历史结果、有限在途调用和结束释放。这里的内存保证目标是：业务负载及配置大小固定时，框架新增保留量由活跃实例和在途任务决定，不随累计消息数或已完成重载次数增长。目标需通过下述结构断言与堆回归后才能标记已验证；仅确认设计不等于已经测得内存稳定。

## 1. 无状态函数为什么仍需关注内存

纯合并函数不保存上轮结果，其局部数组和 Map 在没有引用后可回收。GC 的依据是对象是否仍可达，不是代码是否用了 function、async 或 class。

两阶段 Extra 是函数组合接口，但连接、任务和资源管理仍有副作用。即便业务回调没有可变全局变量，等待 IO 的异步调用也可能持有输入、局部数据和 continuation；调用数量持续增加就会增加在途内存。Promise 不会仅因被创建就永远存活；真正问题是仍被 IO、定时器、调用栈或其他活动引用保留的异步链。

| 场景 | 是否自然积累 | 处理 |
| --- | --- | --- |
| 合并完，结果及局部变量不再被引用 | 通常不会持续增长 | 允许 GC 正常回收，不手工保存历史 |
| 单实例闭包持有一份有界配置 | 有界常驻，属于正常开销 | 卸载后删除实例和 handler 引用 |
| 回调每次从外部取得大对象并塞入全局 Map | 会随 key 数增长 | 本方案不新增该缓存；宿主自己缓存需自行给出界限 |
| 消息比 IO 处理更快，无界 Promise.all | 在途量增长 | 既有接纳上限加有限回调槽位，不批量无限启动 |
| Promise.race 超时后原 IO 未退出，立即再开下一次 | 原操作仍可能持有数据 | 超时只结束本轮等待，原操作真正结束前不释放槽位 |
| 每轮 addEventListener/setTimeout，没有 finally 清理 | 可能积累 | 成功、失败、取消均清定时器并移除监听器 |
| 已完成快照被 session/store/status/日志继续引用 | 历史量增长 | 任务结束按既有重试合同释放，不新增 lastContexts/history |
| 卸载后 registrations/status handler 仍捕获旧实例 | 重载次数增长 | 释放旧函数及配置引用；清理失败时禁止叠加新实例 |

函数闭包并不必然复制其捕获对象；它会延长仍被引用对象的寿命。也不假定引擎总能精确裁掉词法环境里无关的大对象：避免在装配 lambda 周围绑定整份历史、图片或大结果集合。

## 2. 选定的资源约束

下列新增数值为本方案推荐初值，非现有实测上限；实施时先按此实现并验证，若需调整，在验收记录中说明依据。已有 Context、Bot、消息和执行窗口上限继续独立生效。

| 资源 | 目标上限 / 行为 | 作用域 |
| --- | --- | --- |
| 动态加载同时未结束的外部调用 | 默认 8，硬上限 32 | 每个 Channel Extra 实例，涵盖其全部 Bot |
| 单次动态加载期限 | 默认 5,000 ms，可设 1–30,000 ms，包含边界 | 每次实际调用；取得槽位后开始计时 |
| 动态加载等待队列 | 不新建 | 槽满立即 IM_CONTEXT_LOAD_BUSY，原消息队列仍按已有上限接纳 |
| 动态返回及最终 Context | 最多 32 项、UTF-8 JSON 最多 65,536 字节 | 复用现有 v3 预算，分别检查 |
| 单 loader 已接纳未结束的 load 操作 | 最多 64，含执行中与排队 | 每 loader；超限立即拒绝，不持有新 config/dependencies |
| 对同名的重复卸载 | 共享同一在途清理 Promise | 不为每次请求追加等待操作闭包 |
| 动态结果缓存 | 0 份历史缓存 | 当前任务及其既有重试快照之外不存储 |
| 初始化闭包 | 每个加载实例一个 | 不随消息累计生成 initializer |

动态加载的两项可调值写入普通 JSON `config.context_loading = { timeout_ms, max_in_flight }`，作用域为 Extra，省略使用表中默认值。它不是 Context envelope 的字段，不放函数和 signal。两个 Channel 的 config-schema.json 与运行时校验同步新增；错误值在启动前明确拒绝，不悄悄截断到边界。

8 个回调各返回一份合法最大 envelope，其序列化总量最多约 512 KiB；这是结果数据的一份序列化量估算，不是堆或 RSS 上限。合并副本、字符串表示、外部 IO 数据、已提交 Provider 任务和既有消息队列仍有额外开销。不能用 512 KiB 宣称整个插件只有这点内存。

load 操作上限需在复制配置和创建长 Promise 链之前判断。卸载/关闭作为释放资源的操作不能被加载队列满额拒绝；inspect 不为每个请求创建无限排队任务，可读取有界生命周期快照，业务状态查询继续遵守现有同步 handler 合同。配置 clone 只做必要的所有权隔离，不按调用链每层重复复制。

## 3. 超时不是强制终止

调用前同步占用一个槽，创建子 AbortController，并关联 Extra signal 和当前轮实际取消。启动一个超时计时器。任何路径都只能调用一次业务回调。

正常完成时取消计时器、移除关联监听器、完成协议校验；返回结果建立自有快照后释放外部引用。失败时同样清理；所有 Promise 的拒绝均被消费，不产生 unhandledRejection。

达到期限时 abort 子 signal，本轮报告超时并停止进入 Provider。**外部 Promise 尚未结束时仍占槽**，其迟到结果被丢弃。插件不会因超时反复启动无限个替代任务。回调真正 resolve/reject 后才释放该槽；迟到回调不得回写新一轮、session binding 或状态正文。

不合作回调占满槽位后，后续轮次明确报忙，不追加无限等待队列。该保护换来的是可用性下降，但保住新增在途数量的边界。其他未占满的 Extra 独立运行。不要一超时就自动整体重载来绕过仍在运行的操作。

用于处理迟到结果的 continuation 只捕获小型操作令牌、计数器和必要清理动作，不能捕获整条消息、图片、展示对象或所有静态 Context。当前轮失败收尾后释放这些大对象。挂起 Promise 的实际内存由其自身和外部 IO 行为决定，不能仅从 Promise 个数推导绝对字节上限。

## 4. 取消与卸载

卸载先停止接纳并 abort 全部动态操作，再等待受管操作与既有清理。合作式回调应尽快 reject/return；每轮计时器及监听器在 finally 中移除。成功清理后实例不得被 status handler、操作队列或注册表继续持有。

单个卸载推荐使用 5,000 ms 资源清理宽限，从停止接纳并 abort 时开始；初始化退出、动态回调和 disposer 共用此期限，不各自再等一轮。整体停止时全部本地 Extra 也共用一个 5,000 ms 期限，不按实例数量累加；随后继续尝试既有 daemon 关闭流程。该初值需验证是否满足现有连接和任务的实际取消合同。仍有不合作操作时，明确返回 `EXTRA_DISPOSE_FAILED`，保留阻止同名重载的失败实例及必要清理引用，不标 disposed、不自动创建新实例。重复 unload 不能产生新后台任务。所有操作后来结束时可重新完成剩余清理，再由宿主显式决定加载。

父级宿主关闭仍须尝试清理其他 Extra 并执行既有执行服务关闭，报告失败，不因为一个 callback 就吞掉停止结果。不能以本任务授权为由杀掉任意宿主进程或删除其身份、配置和工作目录。

同进程 JS 无法抢占同步死循环。若宿主在回调里无限分配、死循环或自行建立无界全局缓存，本插件无法提供绝对 OOM 保证；signal 和 setTimeout 此时也可能无法及时运行。外部实现必须是可信、有限工作量的业务代码，IO 必须传 signal 并限制响应体。为本需求不新增 worker/进程隔离层。

## 5. 返回结果的预算检查

现有 assertContextEnvelope 最后使用 JSON.stringify 计量。直接对外部返回的巨大对象执行 stringify，再发现超限，仍会制造过大的临时字符串；先 structuredClone 同样可能过量分配。

因此实施前须补齐结果边界：先检查数组长度，再用有预算的普通 JSON 遍历校验值、循环、字符串 UTF-8 字节、嵌套深度及遍历节点，超限立即退出；预算内才执行既有完整 v3 校验和必要 clone。不得调用 getter/toJSON 来制造另一份巨大结果。

实现优先扩展/复用现有 JSON 校验工具，具体文件在 M0/M2 核对后确定，不新造 Context 编译器。检查目标必须覆盖：已超长的单字符串、很深嵌套、数量巨大的小属性、循环引用及非 JSON 对象；预算验证自身不能用无界递归造成栈溢出。最终准确预算仍按既有 UTF-8 JSON 口径，不改变合法协议语义。新增遍历资源限制若会拒绝现有合法数据，须明确记录并评估，不隐含修改整个 v3 合同。

返回值在进入插件前已由外部代码分配，入口检查无法撤销这次分配。应向宿主提供示例：在数据库查询中限制行数、HTTP 流读取时限制字节，不先读取无限响应再过滤。

## 6. 纯函数与副作用分开验证

合并函数测试只证明替换、顺序和不修改输入，不用堆测试证明 GC 引擎本身。内存验证针对资源是否释放、数量是否有界。

结构性断言必须包括：

- 顺序执行 10,000 个新逻辑轮，结束后动态在途数为 0，无历史 Context 容器增长。
- 同时发起超过 max_in_flight 的不同会话，实际进入 callback 的数量不超过上限；满额失败不 invoke。
- callback 不合作时反复超时，原调用数不超过上限；迟到拒绝被消费，结束后槽位归零。
- 每轮成功、失败、超时、取消后 listener/timer 计数回到基线；测试自身不得用 calls 数组保留所有输入。
- 100 次 load/unload 后，不留旧 config/dependency/status handler/连接，失败清理不允许继续叠加实例。
- 1,000 个并发 load 请求只接受至多 64 个，拒绝部分不捕获完整配置，unload/close 仍可执行。
- 动态超大、深层、循环对象在复制/序列化前失败；Provider 调用数为 0。

堆验证在独立 Node 子进程用 `--expose-gc` 执行，预热前 1,000 轮，再比较第 10,000 轮清空测试采集器并 GC 后的 heapUsed。推荐沿用现有 session 调度测试的增量小于 8 MiB 门槛，并加入动态 Context 场景；此为自动化验收阈值，不是进程最大内存承诺。热重载做同类重复采样，记录 heapUsed、external、arrayBuffers 和 RSS。

先以结构断言为准，堆增量超过阈值时取多轮采样和 heap snapshot 定位引用；不得通过无限放宽阈值掩盖线性增长。RSS 可能受 allocator、Provider 和原生库影响，不以单次 RSS 未下降证明 JS 泄漏。现有测试入口：[session 调度回归](../../../test/im-session-scheduling.test.js)、[Extra 生命周期](../../../test/extras.test.js)、[Channel 清理](../../../test/im-extra-disposal.test.js)。

自动化使用 fake Provider 与受控 IO。真实联调在 im-test 验证动态内容、超时展示、取消和重载，不在共享测试环境压入 10,000 次真实模型调用。最终记录实际堆数据、构建版本及未覆盖的外部回调类型，不能只写“函数式所以安全”。
