# 调用请求 32 MiB 总量与图片 IPC 修复

## 状态与已确认决定

状态：已实现，并通过定向回归与 im-test 独立 Host 实测。用户将先前 5 MiB 的决定更新为“整个请求最多 32 MiB，单图保持 2 MiB，历史仍只取纯文本”。四张 2 MiB 图片经 base64 约 10.7 MiB，主输入及 fallback 重复约 21.3 MiB，因此采用 32 MiB。每份请求的文本、Context、图片 base64、显式恢复输入及实际发送的可信执行环境和包装都计入总量。验证见[交付记录](../../journal/shared/2026-10-16-invoke-size-delivery.md)。

现有[独立图片专项](../channel-image-input/brief.md)支持 Codex 独立图片，[多模态协议](../../../packages/octo-runtime-protocol/src/multimodal.ts)允许单图 2 MiB、每组最多 4 张。审查用约 787 KiB 合法 PNG 构造约 1.05 MB RPC，触发 [RPC 服务端](../../../packages/octo-runtime-adapter-host/src/rpc.ts) 的 512 KiB 单行限制及未处理的 readline 错误，导致共享 Host 退出。原真实识图脚本直调 AdapterHost，没有覆盖 daemon 到独立 Host 的完整路径。

## 大小合同

1. 统一常量为 32 * 1024 * 1024 = 33554432 字节。按 UTF-8 JSON 字节计量，不按 JS string.length、解码图片大小或模型 token 数计量；换行分隔符不计入。等于上限允许，大于上限拒绝。
2. 对 NDJSON/JSON-RPC 路径，计量实际单个执行请求的完整 JSON 帧，含 envelope 和 executionEnvOverrides。发送端在写入管道前校验；每一跳都不能依赖另一跳的包装恰好一样大。普通内存 invoke 同样校验其完整提交对象，不能借“没有 IPC”接受无限请求。跨入口边界测试用各入口实际序列化后的请求，不把 inputs 恰好 32 MiB 当作整个请求合法。
3. 单图上限仍为 2 MiB，每组最多 4 张、原图片原字节约束仍校验；同时满足组限制与整请求 32 MiB 才能执行。8 MiB 是既有每组原字节上限，不能解释为允许绕过新整请求预算。主输入和恢复输入重复携带图片时按真实 JSON 分别计费，不按 sha256 去重或假装只传一次。
4. 请求上限与响应帧上限独立。不得把 Provider/Host 单事件、源流窗口、回复文本或所有普通 RPC 的响应限制机械放大为 32 MiB。Provider 自身请求额外编码的开销按其接口处理，不把本文 32 MiB 声称为外部 HTTP 整包大小。
5. 更新 CLI、SDK、daemon、stdio Host 和已暴露的其他执行入口的前置检查；现有 CLI/SSE 16 MiB 整请求说明需要同步，避免同一调用绕入口获得不同无限量路径。必要的 framing 接收器使用同一执行上限，并保留非执行方法原有的更小上限；实现不得先无限读取再检查。

Codex canonical 图片调用会收到携带输入图片的 userMessage/turn 等原生回显。该执行的原生接收行仍受 32 MiB 硬限约束；只有已知输入回显载体、且仅扣除与本轮已提交图片完全相同的 data URL 后剩余内容不超过 256 KiB，才允许继续正常转换。转换器接收原始消息，不把图片回显发成输出事件。其他大事件和 native 模式保持 256 KiB 上限。canonical 的 thread/resume 显式请求 excludeTurns，避免返回完整旧历史；不改变 Provider 自己保存和恢复会话的方式。本机 Codex 导出协议及真实图片后续聊已验证此参数。

## 多图和历史恢复的责任

当前 IM 自动历史明确只有 15 条/1500 字符纯文本，不获取历史图片；单条独立图片仍是一条消息、一张图片、一次调用。群连续发多张图片仍逐条按原门槛处理，不新增批量聚合，也不把相邻 @ 当作授权。

通用 invoke 调用方已经可以显式提交多图和 freshFallbackModelInputParts，本计划对这一现有路径做预算验收：

- 业务方在获取历史材料时知道来源和时间，才可在提交前筛选“可选历史图”。优先保留当前消息图片，再按历史的新到旧依次保留；旧图放不下时舍弃旧图，已保留材料最终按原业务顺序发送。
- 从较新历史开始选择；若加入某图会超过 32 MiB 或每组图数限制，就不加入该图及更旧图片，保留已经选定的较新集合。不截断 base64、不拼坏图片、不把大图改成 URL 假装可见。
- 当前消息的图片、明确必需的恢复材料、用户正文及其他业务显式提交的 Context 不由 Host 自动删除。只靠原始 inputs 数组不能可靠推导时间和“可丢弃”属性；缺少来源时原样校验，超限就拒绝，不猜测最新图。
- 候选集合和下载过程也必须先有界，不能先无限拉历史图再筛到 32 MiB。现有 IM 不新增此下载路径；其他业务方有实际恢复来源时，在其业务模块实现选择，不往通用 renderer 塞历史策略。
- 无可丢弃历史、或保留当前图与必要材料后仍超过 32 MiB，直接拒绝本次请求；不能删掉当前图片后继续文本执行。Provider 恢复需要的当前图仍遵循 assertImageRecoveryParts，不因本计划放宽完整性。

该筛选是调用方明确构造本轮输入，不是 Host 按 sessionId 补齐、合并、去重或自动裁剪 Context。不新增图片持久库、通用历史管理器或协议时间戳字段。

## 超限与连接保护

正常客户端在发送前抛出稳定的 INVOKE_REQUEST_TOO_LARGE，不发出请求、不启动 Provider。Channel 把当前图片/请求超限作为本条消息的可观察失败，沿用错误回复，不自动重试同一超限输入，也不重新建连接补发。

接收端对绕过前置检查的超长行做流式有界处理：计数到阈值后停止保留该行内容，丢弃到换行；不把截断文本交给 JSON.parse。能安全关联原请求时返回受控错误；无法关联时由发送端有限超时终结该调用，不伪造执行成功。读取器必须处理 input 和 readline 的 error，不因超长行调用整个共享 Host shutdown。

异常且永不结束的超长行要有有限读取时长并最终关闭故障传输；这属于破坏 framing 的异常连接，不能混同于一次合法客户端请求超限。正常超限请求不得使其他在途 Run 失败，也不得把固定上限简单放大后保留原有未处理 error 崩溃路径。

## 验收矩阵

| 场景 | 必须观察的结果 |
| --- | --- |
| 合法约 787 KiB PNG、单图恰好 2 MiB | 请求总量合格时经真正 RPC Host 成功识图，不只测 direct Host |
| 整请求 32 MiB - 1、恰好 32 MiB、32 MiB + 1 | 前两者接纳；后一项 Provider 启动次数为零，稳定错误且连接可继续 |
| 图片加正文、Context、可信环境、恢复图重复 | 计入所有实际字节；base64 膨胀和多层包装不能遗漏 |
| 1/2/4 张有效图及超过组数上限 | 在总量内的合法组合按既有能力运行；图数或总量超限分别拒绝 |
| 有时间来源的可选历史图超预算 | 保留当前图及最新可容纳历史；先删旧图、不截字节，排序确定 |
| 当前图/必要恢复材料独自超预算 | 整次明确失败，不能静默丢图后执行 |
| reset 与新 session 自动历史 | 仍只有纯文本，无历史图下载、无新增本地文件 |
| 一个超限请求与另一个长任务并行 | 超限调用失败，另一任务与共享 Host 存活；下一合法请求成功 |
| 分段超长行、无换行、readline error | 缓冲有界；错误受控，故障连接按有限时长退出，不出现 uncaught error |

使用专用 im-test Bot/群上传一张明显超过旧 512 KiB framing、但小于 2 MiB 的真实图片，确认经 daemon 所管理的独立 Host 得到正确回复；只输出尺寸、大小、摘要及结果，不保存图片正文。精确字节边界与故障帧用本地 fixture，线上正常识图不能替代错误隔离测试。运行类型、lint、完整协议和跨入口回归；Run=7 与 Context=v3 不变，不添加能力门槛。
