# IM 接入

## 责任边界

- 负责：从本地文件读取 bf_token，通过 IM Server 注册接口取得 WS 凭据；独立连接 IM 二进制 WS，接收私聊文本，构造固定 Context v3 和发起人元数据，通过 Daemon 注入的 AdapterHostRpc 执行，并一次回发最终文本。
- 不负责：启动 provider、创建第二个 Host/Daemon/CLI、云端 Event/Run 登记、Worker SSE、聊天 SQLite、群聊、GROUP.md、卡片或 typing。
- 本地执行不依赖旧 octo-agent-access 或 Worker。远端模型和 IM Server 仍需网络；WS 发送回执只代表服务端接纳，不代表客户端已经显示。

## 配置与启动

使用已有 CLI：`octo-harness --home <绝对路径> daemon run`。Daemon 读取 `<home>/im.json`；文件不存在时不启动 IM 接入。配置格式为 `{ "bots": [ ... ] }`，每个 bot 包含：

| 字段                  | 含义                                                             |
| --------------------- | ---------------------------------------------------------------- |
| id / botId / spaceId  | 本地配置名、注册返回的机器人身份、租户身份                       |
| apiUrl                | IM API 根地址，例如 `https://im-test.deepminer.com.cn/api`       |
| tokenFile             | bf_token 文件路径，相对路径以 Home 为基准；POSIX 权限必须为 0600 |
| adapterType / workdir | adapter 名称和固定绝对工作目录                                   |
| context               | 有效的 `octo.context-envelope/v3` 固定上下文                     |
| model                 | 可选模型                                                         |
| allowedSenderIds      | 可选私聊发送者白名单；默认只接受注册返回的 owner                 |

每个 Home 最多 16 个 bot，同一服务的 botId 不能重复。各 bot 独立持有 WS、加密状态和会话映射，共享一个 adapter-host。不同 Home 不会自动合并；同一 bot 应由一个 Home 管理。

## 会话与限制

会话按 space、bot 和私聊对方隔离。`/session` 返回本地 session、generation 和最近 runId；`/reset` 在前序轮次完成后清除 provider 会话句柄、增加 generation，保留本地 sessionId。每个会话串行执行，普通轮次采用 `full_access`，执行上限 120 秒。

只保存有界内存中的会话句柄与入站去重记录，不保存聊天历史。重启后会话映射和去重窗口消失，不保证进程崩溃后的补发。最终文本最大 256 KiB；每个 bot 最多 128 个会话、64 个排队轮次。发送失败不代表执行可以安全重跑。

## 验证

`test/im-runtime.test.js` 覆盖注册、加密 WS、最终文本、会话复用、/session 和 /reset。2026-10-13 使用 im-test 的 Codex 测试机器人完成真实入站 → 本地 Codex → WS 回发；服务端历史确认两次最终答复。客户端显示和真实 /reset 交互尚未取得用户确认。

## 为什么都用 JSON-RPC 2.0，还需要统一 AgentRun 协议？

JSON-RPC 2.0 统一请求、响应、通知与错误的消息格式；AgentRun 统一“一次 Agent 执行”的业务合同。统一 AgentRun 可以继续使用 JSON-RPC 2.0，无须另造 RPC 格式。仅有相同的消息格式，不意味着方法、参数、状态和执行保证相同。

| 层次              | 解决的问题                                                           | 本项目中的例子                                                                  |
| ----------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 传输              | 消息通过什么连接发送                                                 | stdio、UDS / Pipe、WebSocket；未来云端接口按实际服务适配                        |
| RPC 消息格式      | 怎样表达调用、关联响应、推送通知和返回错误                           | JSON-RPC 2.0 的 `id`、`method`、`params`、`result`、`error`                     |
| Agent 执行合同    | 执行什么、属于谁、如何传入 Context、怎样取消、何时完成、如何交付结果 | AgentRun、Context v3、统一执行事件与交互语义                                    |
| Provider 原生协议 | 某个执行器的具体调用方式                                             | Codex 的 thread / turn / item；未来 Serverless Agent 的任务提交、查询或回调接口 |

Codex app-server 使用双向 JSON-RPC 风格协议，公开 `thread/start`、`thread/resume`、`turn/start` 等方法。官方文档还注明其线上消息省略 `jsonrpc` 字段，因此不应把“都基于 JSON-RPC”理解为消息可不经适配直接互通。[OpenAI 官方 App Server 文档](https://developers.openai.com/codex/app-server)

如果产品只调用 Codex，直接采用它的 thread / turn / item 合同是合理选择，可以减少映射成本。本项目同时接入多种本地 Agent，并计划接入云端 Serverless Agent；若把 Codex 原生合同作为所有入口的公共接口，其他执行器就需要模拟 Codex 的会话、工作区、交互和事件对象，上层也会跟随 Codex 原生接口变化。

统一层的价值是让 IM、Loop、Work App 按同一种执行语义工作：发起一次 Run，传入 Context，消费公开进度，回答交互，请求取消，确认终态和产物。Codex Adapter 负责映射到 Codex 原生调用；其他 Adapter 映射到各自原生接口。当前已有的对应关系见 [Host RPC](../octo-harness-adapter-host/src/rpc.ts) 与 [Codex Adapter](../octo-harness-adapter-codex/src/app-server.ts)。

### 面向云端 Serverless Agent 的设计理由

以下是目标适配场景，不是已经实现的云端能力。假设某个云端 Agent 提交后返回任务 ID，随后通过查询或回调提供结果，且没有本机进程、固定工作目录或可恢复的 Codex thread。它仍可通过适配层履行 AgentRun 合同，上层无需识别该服务的专有任务格式。

| 上层需要的语义 | 本地 Codex 映射                          | 未来 Serverless 映射示例                                       |
| -------------- | ---------------------------------------- | -------------------------------------------------------------- |
| 发起执行       | 准备或恢复 thread，再启动 turn           | 提交云端任务并保存原生任务 ID 的关联                           |
| 跟踪一次 Run   | 关联本次 invocation 与原生 thread / turn | 关联本次 Run 与云端任务；RPC 响应不等于任务完成                |
| 消费结果       | 将原生 item / turn 事件映射为统一事件    | 将查询、SSE 或回调结果映射为统一事件，只报告实际可观察的信息   |
| 取消与交互     | 调用原生中断或响应接口                   | 使用服务实际支持的取消或交互能力；不支持时明确返回限制         |
| Context 与资源 | 应用本地准备结果和原生运行配置           | 使用授权资源引用及云端可接受的输入，不能直接传本机路径         |
| 断线与超时     | 依实际会话、进程和事件状态判断           | 查询原任务或报告结果未知；不能因连接超时认定任务失败并重新提交 |

这里需要分别保留 JSON-RPC 请求 `id`、业务 `run_id` 与 Provider 原生执行 ID：请求 `id` 只关联一次 RPC 往返，不能单独承担跨连接追踪、提交幂等或授权。更换传输连接不应改变同一次 Run 的身份。执行位置变为云端，也不意味着必须先经过云端 Event 登记；执行器适配与 FEAT-IM-006 的可选登记是两个独立问题。

统一合同会带来映射与维护成本，因此只统一上层确实依赖的执行语义。不要复制 Codex 的全部管理 API，也不要把所有执行器压成只有文本的最低共同能力。Provider 特有能力由 Adapter 明确处理；不支持必需语义时应拒绝请求，不能伪造取消、恢复、Context 应用或完成证据。可选扩展继续遵循当前合同的未知字段处理规则。

## 待实现：Channel 业务与上下文能力

本章只列需求，不代表代码已实现。上文描述当前私聊基础；以下梳理原 Channel、旧 daemon 中的额外职责，以及新 IM 包需要补齐的能力。**MUST** 表示目标实现必须满足的要求，**MUST NOT** 表示禁止行为。依赖尚未确定的接口或产品取舍列在章末，不将其写成现有能力。

### 接入、身份与触发

#### FEAT-IM-001：模块边界与宿主装配

- **功能点**：让 IM 成为 Daemon 装配的独立入口，复用共享执行 Host。
- **MUST**：通过依赖注入获取 Host、身份与授权资源读取能力；由宿主管理启动、停用和异常清理。群规则、历史选择和投递决策留在 IM 包。
- **MUST NOT**：另建 CLI、Daemon、默认 Host 或 Provider 执行器；把任务归档、讨论产物、Worker 注册等非 IM 业务整包搬入；仅为调用 Host 强制实例化 worker-access。
- **验收点**：多个 IM Bot 与 Worker 入口共享 Host；停用一个 Bot 不终止其他入口。

#### FEAT-IM-002：Bot 绑定、身份授权与配置校验

- **功能点**：验证服务、Space、Bot、owner、Agent 与当前接入实例之间的关系。
- **MUST**：使用认证结果和授权配置确定身份；验证发送者、群成员资格及可访问范围。完整校验配置类型、重复身份、地址和凭据文件权限；缺失身份与身份不匹配分别报错。
- **MUST NOT**：信任消息正文中的 `space_id`、Agent ID 或 owner 声明来扩大权限；把业务 ID 当凭据；把 Bot token、IM token 或用户凭据加入 Context、模型输入、回复或日志。
- **验收点**：伪造租户、跨群引用、被撤权成员及重复 Bot 配置均不能启动执行。

#### FEAT-IM-003：IM 连接与单一接入所有权

- **功能点**：补齐 WS 认证、心跳、重连、凭据轮换与重复接入处理。
- **MUST**：区分离线、认证失败、禁用与可重试网络错误；重连退避且有上限，关闭旧连接与定时器。标记连接代次，使旧连接晚到消息失效；明确多个进程争抢同一 Bot 时谁可接收和回复。
- **MUST NOT**：无限快速重连；同时保留多个有效接收者；把传输层 ACK 解释成已创建 Run 或已完成业务消费。
- **验收点**：断网恢复、凭据失效、重复启动及关闭期间重连不会产生双执行或残留连接。

#### FEAT-IM-004：消息与会话地址规范化

- **功能点**：统一私聊、群聊、话题、引用、@、编辑和撤回的内部表示。
- **MUST**：保留原始消息 ID、序号、修订、发送者、时间、回复目标和结构化 parts；使用渠道地址规则确定群与话题，不从显示名称推断身份。编辑与撤回按修订更新候选历史，是否另触发执行由显式策略决定；不支持类型明确标记。
- **MUST NOT**：把图片、文件或卡片强制变成空文本后继续执行；将原始 WS 包整体塞进 prompt；用正文中的 `@名称` 代替真实 mention；宣称撤回消息能撤销已发生的工具副作用。
- **验收点**：同名群、话题与主群、消息修订、引用及不支持类型都有确定结果。

#### FEAT-IM-005：群触发与被动上下文

- **功能点**：区分“触发 Agent”与“仅供本群后续上下文使用”。
- **MUST**：明确私聊、@当前 Bot、回复当前 Bot 有效交互、普通群消息的处理规则；普通群消息只进入授权范围内的候选材料，不自动创建 Run。自发消息、其他 Bot 和系统通知有显式过滤规则。
- **MUST NOT**：每条群消息都启动 Agent；把回复其他 Bot 的消息升级为自己的交互；因 Bot 回复再次触发而形成循环；把权限检查交给模型决定。
- **验收点**：同群多个 Bot 只响应各自有效触发；未 @ 的讨论可按历史策略使用，但不产生执行。

#### FEAT-IM-006：Agent 选择、触发幂等与可选登记

- **功能点**：将一次授权触发关联到确定的 Agent、Event / Run 身份和唯一执行目标。
- **MUST**：按授权绑定与显式选择解析 Agent，保留实际选择结果；以完整来源作用域和消息身份去重。若启用云端登记，必须冻结登记接口与执行权交接：同一次触发使用同一 Run，登记响应不明时查询或幂等重交，本地提交与 Worker WS 下发只能由一个入口执行。
- **MUST NOT**：同一触发分别执行本地与云端 Run；超时后换 ID 重试；把本地随机生成 ID 当云端登记成功；擅自换 Agent、引擎或忽略 mandatory；给当前本地链路隐式增加云端依赖。
- **验收点**：重复消息及本地/远端接纳竞争不导致重复 Provider 启动；超出内存去重保证范围时如实说明，不承诺跨重启 exactly-once。

### 会话与上下文连续性

#### FEAT-IM-007：会话作用域与多 Agent 隔离

- **功能点**：将渠道会话稳定映射为 AgentSession 与 Provider Session。
- **MUST**：隔离键覆盖真实租户、服务/Endpoint、渠道、账号（存在时）、Bot、会话、话题及 Agent 消费者。分别维护 session generation、Provider handle 和上下文进度；复用前核对实际执行配置与权限。
- **MUST NOT**：只用群 ID 或用户 ID 做全局会话键；多个 Agent 共用消费游标；跨租户、Bot、话题复用 Provider Session；把归并 key 误改成实体 ID。
- **验收点**：相同群 ID 在不同租户或 Bot 下不共享材料；同群不同 Agent 各自获得尚未消费的上下文。

#### FEAT-IM-008：排队、取消与会话命令

- **功能点**：补齐 `/session`、`/reset`、新会话和停止执行的明确语义。
- **MUST**：同一会话按确定顺序执行，不同会话受全局并发限制；队列有容量与等待期限。停止命令可控制活动 Run，不排在该 Run 后等待；重置定义活动 Run、排队消息和新 generation 的处置，并拒绝旧代次结果回写。
- **MUST NOT**：把控制命令当聊天历史再次喂给模型；重置后复用旧 Provider handle；未经授权让任意群成员取消他人的执行；无限排队。
- **验收点**：运行中停止、连续重置、重置与新消息竞争、队列满和空闲会话淘汰均可观察且不串代。

#### FEAT-IM-009：Context 来源分层与统一编译

- **功能点**：区分当前请求、背景事实、可信规则与执行配置。
- **MUST**：当前用户输入保留独立 parts；历史、引用和普通文件进入 `octo.content/inline` 或授权解析后的资源材料；可信配置才可进入 `octo.control/instructions`。引擎、模型、工作区、环境变量、权限与限额继续使用结构化项；统一合并后校验 v3 并复用 Context Builder。
- **MUST NOT**：在 daemon、IM、worker-access、Adapter 各拼一次相同上下文；将材料伪装成 system 指令；仅用提示词代替工具授权、MCP 挂载或模型设置；在用户可见提问中混入隐藏上下文。
- **验收点**：同一材料只编译一次且可追溯；含“忽略平台限制”的群消息不能改变执行权限。

#### FEAT-IM-010：历史窗口、引用与完整性

- **功能点**：获取触发前的授权历史，组成确定的上下文窗口。
- **MUST**：以触发消息 ID / 序号固定上界，稳定排序和去重；触发消息本身只作为本轮输入出现一次。优先保留直接引用与相关近邻消息，标记完整、部分可用或不可用；查询范围、分页、条数与字节数有边界。
- **MUST NOT**：读取触发后的消息改变本轮语义；扫描其他群、私聊或兄弟话题补材料；用截断结果冒充完整历史；无法读取引用时编造正文。
- **验收点**：窗口边界、乱序、重复、分页缺口、无权限引用、首次进入群和空历史都有可重复的选择结果。

#### FEAT-IM-011：增量上下文与冷启动恢复

- **功能点**：保留旧频道逻辑中 bootstrap、delta、inherit、recovery 的业务含义。
- **MUST**：首次会话提供有界初始窗口；可靠复用 Provider Session 时只提供未消费增量；无新材料且配置不变时明确继承；Session 丢失、重置或配置不可复用时重新准备授权冷启动材料，更新会话代次并标明窗口完整性。
- **MUST NOT**：在空 Provider Session 上只发送依赖旧记忆的 delta；每轮重复发送全部聊天；以模型回复“记得了”作为消费凭证；为恢复而重跑已执行的工具副作用。
- **验收点**：连续两轮不会重复注入历史；Provider handle 失效后建立可解释的新会话，无法补齐时明确缺口。

#### FEAT-IM-012：本轮快照、消费提交与失败处理

- **功能点**：冻结实际使用的历史、规则版本与资源，区分 Context 消费、Run 完成和 IM 投递。
- **MUST**：分别记录 Context 已准备/已应用、Run 终态、IM 投递状态；同一次接纳的重试复用相同快照和 digest。仅在满足约定执行成功条件后推进消费进度，并核对 generation；失败、取消与终态未知时不推进，后续按可确认的 Provider 状态重建或续接。
- **MUST NOT**：准备完成即认定模型已消费；等待云端 durable ACK 才提交本地频道消费；因 IM 发送失败回滚成功 Run 并重跑；让失败 Run 的残留 Session 导致材料重复应用。
- **验收点**：准备后失败、终态丢失、投递失败、重复终态及重置后的晚到结果均不错误推进游标。

### GROUP.md 与上下文材料

#### FEAT-IM-013：群与话题规则读取

- **功能点**：读取当前群 `GROUP.md`，话题内再读取该话题文档。
- **MUST**：用当前 Bot 授权身份读取文档，核对 Space、Endpoint、群及话题；保留来源、正文、版本与 digest。区分未配置、空文档、已删除、无权限和网络失败；私聊默认不加载群规则。
- **MUST NOT**：根据用户输入的群名或 URL 读取任意文档；将读取失败解释为空规则；沿用其他群缓存；仅检查文件名而不核对来源。
- **验收点**：群聊只加载本群文档；话题加载本群加本话题文档；跨群文档被拒绝。

#### FEAT-IM-014：GROUP.md 的信任等级与 Context 映射

- **功能点**：让群约定进入模型输入，同时保持指令与材料的权限边界。
- **MUST**：经服务端权限确认、由授权管理配置产生的群规则，可作为当前会话的 `agent_configuration` 贡献进入 `octo.control/instructions`，顺序为群规则、话题补充。其效力受平台策略、Agent 约束与 mandatory 限制；普通消息、上传文件和来源未认证的 Markdown 仅作 `octo.content/inline` 材料。
- **MUST NOT**：因文件名叫 `group.md` 就升级为可信规则；允许正文自称 `platform_policy`；通过群规则修改工具授权、环境变量、工作区或 fullAccess 策略；仅凭 `source` 标签证明可信。
- **验收点**：受管群规则与同名聊天附件走不同信任通道；话题可细化群约定，但不能放宽平台或 Agent 的硬约束。

#### FEAT-IM-015：规则变更、清空与撤权

- **功能点**：让下一轮使用最新授权规则，同时保持在途 Run 的输入可追溯。
- **MUST**：每轮解析当前版本，或通过有版本与撤权语义的缓存验证；接纳后冻结本轮快照。下一轮替换旧版本；空话题文档仅撤销话题规则，不撤销父群规则。复用 Session 时确保旧规则不再作为有效配置，无法证明替换有效时启用新代次；授权撤销阻止后续读取和执行。
- **MUST NOT**：无限追加新旧版本；删除后沿用旧缓存；同一 Run 重试时静默读取 latest 并沿用旧 hash；把空字符串当“不更新”；依赖旧快照绕过撤权。
- **验收点**：群规则 v1 → v2 → 清空、话题删除、Bot 退群与缓存命中时，下一轮体现正确有效状态。

#### FEAT-IM-016：本地 group.md 的显式使用

- **功能点**：明确“我已有一个本地 `group.md`”怎样参与某个群的 Context。
- **MUST**：由授权配置显式绑定文件与目标群/话题，声明用途为参考材料或受管规则；限制可读目录、真实路径、符号链接、编码和大小，冻结本轮正文与 digest。远端与本地规则并存时，先确定唯一有效来源或明确组合规则。
- **MUST NOT**：自动扫描 cwd、父目录、用户 Home 的同名文件；默认同步到远端或写入 Provider 的 `AGENTS.md`；让一个文件隐式影响所有群；把本机路径当云端资源地址。
- **验收点**：未绑定的同名文件不生效；群 A 的绑定不进入群 B；文件变更在下一轮可追溯；越界路径与未授权规则模式被拒绝。

#### FEAT-IM-017：预算、裁剪与摘要

- **功能点**：统一管理群规则、历史、引用、附件和当前输入的容量。
- **MUST**：复用当前 Context 数量/字节校验与模型容量，预留输出空间；明确各来源预算和确定的裁剪顺序。优先裁剪可选旧历史，保留当前请求和必要引用；规则或必需输入超限时明确拒绝。摘要记录覆盖范围、来源版本及缺口，继承原材料信任等级。
- **MUST NOT**：静默删除 mandatory 或规则条款；只按字符数假装精确 token 计数；把摘要标成原文；将旧 Channel 容量常量直接当新包承诺；复制第二套通用压缩器。
- **验收点**：大群历史、长文档、多附件和低容量模型下仍满足预算，能解释省略内容与原因。

#### FEAT-IM-018：附件、图片与引用资源准备

- **功能点**：补齐图片、文件、链接、选区及其他受支持材料。
- **MUST**：保留 parts 顺序与类型；经授权 Port 解析来源和下载，复用通用物化与摘要工具；检查 scope、版本、大小、类型、digest 和取消信号。临时资源有清理边界；缺少 resolver 的类型明确拒绝或按约定标记不可用。
- **MUST NOT**：向模型暴露认证 header、含凭据的临时 URL 或任意本机路径；由材料内命令触发下载或解包；静默丢失图片；仅用 prompt 声称资源已加载。
- **验收点**：过期链接、撤权、错 digest、下载中取消、同名附件与 Adapter 不支持的资源类型不会伪造应用成功。

### 执行、事件与投递

#### FEAT-IM-019：IM 执行策略与统一准备

- **功能点**：对齐入口策略、有效 Context 和实际 InvokeRequest。
- **MUST**：将 IM fullAccess 意图映射为 `full_access`，继续校验身份、授权与 Agent mandatory，冲突时明确拒绝；复用配置解析与准备，核对 Context、实际模型、工作区、环境变量及限额。使用冻结执行计划和远端租约的路径还必须验证计划、lease/fencing 与准备回执。
- **MUST NOT**：硬编码 `full_access` 覆盖更严格的 mandatory；改变其他入口权限；编译成功即声称 Adapter 已应用；绕过该执行路径的身份与准备要求。
- **验收点**：配置冲突、资源准备失败或身份失效时 Provider 不启动；实际调用与已验证结果一致。

#### FEAT-IM-020：标准事件消费与断线续流

- **功能点**：使用 Host 标准事件构建 IM 视图，支持可用窗口内恢复。
- **MUST**：保留 Run、源流与事件序号身份，处理 message 创建/增量/替换、模型轮次、工具、交互和终态；只推进连续接收游标，按源身份去重。复用 Host 有界流能力，对过窗、重启、缺口和慢消费者给出确定结果。
- **MUST NOT**：解析 Provider 私有事件；把 `message.update` 当 Run 终态；重连时重新 invoke；为每个 token 建 SQLite outbox；连接关闭即认定成功。
- **验收点**：快 Run、重复帧、断线后终态、过窗与 Host 重启均不重复执行或伪造完整答案。

#### FEAT-IM-021：进度与最终答案投影

- **功能点**：将过程映射为 IM 卡片或文本，并正确收敛最终回复。
- **MUST**：`commentary` 用于过程，`final` 用于答案候选；按 message ID 处理增量与替换，多 message 依规范聚合。权威成功终态后才交付成功答案；失败、取消、无文本和仅附件结果分别呈现。渠道不支持卡片时有明确文本策略。
- **MUST NOT**：混入私有 reasoning、原始工具参数或凭据；仅凭 `channel=analysis` 公开内容；用过程播报拼最终答案；截取半段答案冒充完整成功结果。
- **验收点**：analysis 只在 exposure 明确允许时公开；多轮工具、文本替换、失败前已有文本和空成功结果均正确显示。

#### FEAT-IM-022：投递幂等、限流与重试

- **功能点**：为发送、更新、分段和终态回执建立独立投递状态。
- **MUST**：关联 Run、回复目标、业务消息与渠道回执；合并频繁进度更新，限制速率与队列容量，终态优先。区分限流、网络未知、认证失败和永久拒绝；未知结果用查询或幂等发送核对，重试有期限与停止条件。
- **MUST NOT**：API 超时后直接创建另一条最终消息；投递失败改写 Run 成功终态；每重放一个 token 就发一条消息；照搬旧 Channel 的终态无限重试；无持久记录与渠道幂等却承诺跨重启 exactly-once。
- **验收点**：发送成功但回执丢失、429、退群、长文本分段及部分分段成功后的重试，不造成可避免的重复或错误收件人。

#### FEAT-IM-023：文件与产物回复

- **功能点**：将本轮可交付产物作为附件或授权链接返回。
- **MUST**：验证产物属于当前 Run 且允许当前会话访问；明确上传、链接有效期、大小限制与失败状态，保留最终答案关联。文本和附件分别记录投递结果。
- **MUST NOT**：自动上传整个工作区；公开本机绝对路径、密钥或其他 Run 产物；附件失败却声称全部交付；更换下载目标绕过授权。
- **验收点**：仅附件、文本成功但附件失败、重复上传与链接过期有明确表现和重试边界。

#### FEAT-IM-024：交互请求、用户回答与审批响应

- **功能点**：承接选择、补充输入及实际出现的权限交互。
- **MUST**：交互 ID 绑定 Run、会话、可响应者与期限；关联卡片操作或引用回复，经同一 Host 回答有效请求；处理重复点击、超时、取消、重置和误答，遵循独立 approval 协议。
- **MUST NOT**：把任意群消息当批准；将旧交互回复投到新 Run；因 IM fullAccess 就伪造用户回答；为交互响应额外创建普通 Run。
- **验收点**：回复另一 Bot、无权用户点击、过期按钮与重复回答均不能错误改变执行。

#### FEAT-IM-025：业务通知与渠道扩展边界

- **功能点**：承接授权通知投递，预留其他 IM 渠道映射。
- **MUST**：通知验证生产者、目标 Space/会话及接收权限，复用投递层并独立查询结果；渠道差异收敛到消息、历史、规则与发送 Port。第三方 webhook 的公网入口和验签继续由相应服务承担。
- **MUST NOT**：为发送通知创建模型 Run；重新创建 Task 或修改 Loop 业务状态；把 webhook 服务塞进 Host；未接入真实渠道就宣称多平台可用。
- **验收点**：纯通知不调用 Provider；重复通知按业务幂等处理；其他渠道未实现能力明确暴露。

### 生命周期、隔离与验收

#### FEAT-IM-026：有界状态与恢复保证

- **功能点**：明确仅驻内存的状态及需要另行决定的业务持久化。
- **MUST**：为去重表、会话、历史窗口、快照、缓冲和投递队列分别设置容量、TTL 与清理规则；重启后重新验证身份和 Provider Session，明确历史与投递缺口。若需要持久投递，单独定义记录范围及恢复责任。
- **MUST NOT**：默认复制旧 `ChannelContextStore` SQLite、迁移脚本、云端 outbox 和 durable ACK；把观测日志当消息库；声称仅靠内存能跨崩溃无损恢复；状态淘汰后自动重跑有副作用的 Run。
- **验收点**：长期运行与大量群会话下内存有界；重启后正确报告保证范围，不静默漏答或重复执行。

#### FEAT-IM-027：切租户、撤权与关闭清理

- **功能点**：处理 Space 切换、Bot 禁用、退群、Agent 解绑、凭据失效与退出。
- **MUST**：阻止受影响作用域的新接纳，按生命周期取消或排空在途工作，清理连接、缓存、订阅和临时资源；晚到回调重新校验身份代次。Work App 集成时经 main 的统一认证变更入口登记，凭据只留在 main。
- **MUST NOT**：将旧 Space 结果回复到新 Space；让撤权材料进入下一轮；让 kit 读取宿主全局桥或新增第二个 preload 全局；关闭 IM 时终止共享 Host 上其他入口任务。
- **验收点**：执行与下载期间切 Space、禁用 Bot 或退群，不产生跨作用域读取、回写或投递。

#### FEAT-IM-028：诊断、审计与真实环境验收

- **功能点**：分别定位触发、Context、执行与投递问题。
- **MUST**：用非敏感业务 ID 关联 message → Event（存在时）→ AgentSession → Run → delivery；记录触发/忽略原因、材料来源与版本/digest、历史范围和缺口、准备/应用状态及投递错误类别。后续实现逐 FEAT 验收，使用 `https://im-test.deepminer.com.cn/` 与真实授权链路验证；涉及 UI 时需 CDP 驱动真实 renderer。
- **MUST NOT**：用“加载成功”代替应用或调用证据；日志默认收集群正文、规则全文、附件内容或 token；只通过 mock 就标记线上完成；将本次 README 整理表述为本章功能已联调通过。
- **验收点**：覆盖私聊、群聊、话题、多 Bot、多 Agent、规则更新/清空、跨租户、断线、重复触发、取消、撤权和投递失败；分别记录真实结果与未验证范围。

#### FEAT-IM-029：统一执行合同与云端 Serverless 适配边界

- **功能点**：使 IM 使用同一 AgentRun 语义接入本地和未来云端执行器。
- **MUST**：复用现有 Protocol、Host 与 Adapter 扩展边界；统一输入、执行身份、公开事件、交互、取消和终态含义。云端适配需明确接纳与完成的区别、原生任务 ID 映射、超时未知、幂等提交及实际可用的查询/续流保证；凭据、资源可达性与租户授权在执行边界校验。
- **MUST NOT**：因底层都用 JSON-RPC 就透传 Codex 方法给所有执行器；让 IM 按 Provider 分支解析协议；要求 Serverless 伪造本机进程或 Codex thread；以 RPC 成功表示 Run 完成；仅为未来接入修改 Run=7 或 Context=v3 的版本。
- **验收点**：接入一个真实云端执行器时，IM 的触发、Context 分层与投递逻辑不新增该 Provider 的专有分支；提交超时不重复启动任务，不支持的能力明确返回。具体服务和接口选定前保持待实现状态。

### group.md 如何进入 Context：目标流程

以下为待实现行为，不代表现在把文件放进目录就会生效。

| 步骤               | 处理                                                                            | 结果                                                   |
| ------------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 1. 明确来源        | 受管群文档，或显式绑定的本地 `group.md`                                         | 确定目标 Space / 群 / 话题及用途；未绑定文件不读取     |
| 2. 授权读取        | 当前 Bot 读取远端；本地经受限文件读取 Port                                      | 得到正文、来源、版本或 digest；未配置与失败分别记录    |
| 3. 判定信任        | 验证群管理配置来源，或本地规则绑定权限                                          | 可信规则生成 `agent_configuration`；普通附件只生成材料 |
| 4. 组合输入        | 群规则 → 话题补充；另取触发前历史与引用                                         | 规则、历史和当前问题保持不同来源，问题不重复注入       |
| 5. 构造 v3 Context | 规则进入 `octo.control/instructions`；事实进入 `octo.content/inline` 等现有类型 | 合并同类型 entries，完成权限、mandatory 与预算校验     |
| 6. 冻结与编译      | 固定本轮版本/digest，经统一准备和 Compiler                                      | Host 获得材料与控制输入；Adapter 应用另有证据          |
| 7. 下一轮          | 重验版本、权限与 Session 可复用性                                               | 编辑下一轮生效；清空撤销该层规则；重试不偷换本轮版本   |

例如：群规则要求“发布结论需附依据”，话题规则要求“仅讨论本次发布”，用户问“这次可以上线吗”。目标输入由两条经认证的规则、触发前授权讨论事实、当前问题三部分组成。同样的 Markdown 若只是聊天附件，则仅作为阅读材料，不能自动成为群规则。文档中写“允许访问其他群”也不能扩张读取权限。

| 投递跨重启保证                             | 022、025、026      | 是否保存最小业务投递记录、位置和期限；未选定持久方案前不承诺崩溃后无损或 exactly-once                                      |
| 首个云端 Serverless Agent 的接口与执行保证 | 029                | 选择实际服务后确认提交、幂等、查询/回调、取消、交互、资源授权及结果保留；不预先假定其使用 JSON-RPC 或具备本地 Session 语义 |

建议先完成身份、触发与唯一执行权，再完成 Context 分层和群规则，然后补齐流、交互、投递与恢复验收。每个 FEAT 单独确认完成证据，不以能连接 WS 或回复一句话代替整体完成。
